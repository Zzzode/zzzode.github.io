口径说明：本文依据 Kotlin 官方文档（kotlinlang.org，2026-09-23 核对）的 Java 互操作章节与 K2 编译器迁移指南，编译器内部结构参照开源仓库 JetBrains/kotlin 的模块划分。这是一篇语言设计分析，不是上手指南——重点回答一个类型系统问题：**当一门强制空安全的语言必须消费一门没有空安全的语言的全部代码时，类型边界该怎么设计。**

</Prose>

  <Prose tile>

Kotlin 的立身之本是把 null 放进类型系统：`String` 保证非空，`String?` 才可空，错误在编译期暴露。但它的生存策略是**100% 与 Java 互操作**——不是另起炉灶吸引少量新代码，而是让现存的海量 Java 库（以及 Android 当时的全部 API）可以直接被 Kotlin 调用。

这造成一个尖锐矛盾：**Java 的任何引用类型在签名层面都可能为 null**。如果 Kotlin 保守地把所有 Java 返回值都当作 `String?`，那调用任何 Java API 都要写一堆无意义的空检查，互操作啰嗦到不可用；如果激进地当作 `String`，空安全承诺就是谎言，运行时 NPE 会从 Java 代码里漏进来。

Kotlin 设计师的答案不是二选一，而是在类型系统边界引入第三种东西：**平台类型（platform types）**。同时，编译器本身也在 2024 年 Kotlin 2.0 迎来 K2——一个用统一前端 IR（FIR）彻底重写的新前端，把包括 Java 互操作在内的解析、调用决议与类型推断做得更一致、更快。

  </Prose>
</Section>

K2 的「根本性变化」（官方原话）是**一个包含更多语义信息的统一数据结构**。旧前端 PSI/FE1.0 时代，命令行编译器与 IDE 各自重复实现分析逻辑，对 Java 类型的处理在不同入口可能不一致。FIR（Frontend IR）作为语义分析、调用决议与类型推断的统一中间表示，让「一个 Java 方法在编译器和 IDE 里被如何解读」只有一个答案——这对平台类型这种跨语言推断尤其关键，也让新语法糖的引入不再需要同时改三套代码。统一的 JVM/JS IR 后端在 K2 之前先行落地，K2 补齐的是前端，至此整个编译器管线围绕共享 IR 重组。
