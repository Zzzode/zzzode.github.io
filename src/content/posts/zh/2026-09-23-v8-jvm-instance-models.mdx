  <Prose>

Chrome、Node.js 把 V8 当 C++ 库链接进自己的进程；JVM 从第一天起就是一个被宿主启动、也可以被 native 程序反向启动（JNI Invocation API）的运行时。一旦你的进程里住进这样一个房客，三个问题立刻出现：**它能复制出几份（实例拓扑）？你家的几条线程能不能同时进它家门（进入协议）？它搬走时你手里留的钥匙还算不算数（销毁与悬垂）？**

本博客 [Edge.js 一文](/posts/2026-09-23-edgejs-inprocess-dotnet/)讲过两个运行时同进程共处时的封送、线程与跨 GC 生命周期问题。本文往底层再走一层：不讨论两个运行时怎么对话，而对照 V8 与 JVM 各自如何定义「运行时实例与宿主线程的关系」。先记住读图的总纲——**「有几个 VM 实例」和「一个 VM 里有几个线程在执行」是两个正交的问题**，两套设计是这两个轴上的相反组合。

  </Prose>
</Section>

      ["长期", "Persistent / Global 句柄，显式 Reset", "Global reference，DeleteGlobalRef 释放", "全实例/全 VM 根，负责保活到显式删除"],
      ["弱引用", "（通过 SetWeak 等弱化回调）", "Weak global reference", "不阻止回收，每次使用前必须检查是否仍存活"],
      ["环境层", "Context：同 Isolate 内的独立 JS 全局环境", "（类身份边界由 ClassLoader 承担）", "隔离的是名字空间，不是堆"],
    ]}
  />
  <Prose>

还要注意「保活」与「线程安全」是两件不同的事：global 引用保证对象不被 GC 回收，但**不保证业务数据竞争自动消失**——多个 attached 线程同时操作同一个 Java 对象，同步仍由 Java 侧的锁与内存模型负责；规范层面，跨线程误用线程私有的 JNIEnv、使用已删除的引用都是非法调用。JNI 规范还规定挂起异常（pending exception）期间不允许继续任意调用，native 代码必须显式检查并选择传播或 ExceptionClear——边界正确性靠的是这套分层协议，而不是一把包住一切的大锁。

  </Prose>
</Section>

      </p>
