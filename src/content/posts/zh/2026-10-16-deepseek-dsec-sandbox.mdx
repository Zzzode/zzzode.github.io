先交代来源。本文事实全部来自 DeepSeek 2026 年 9 月 19 日挂上 arXiv 的论文《DeepSeek Elastic Compute (DSec): A Sandbox Infrastructure for Effective Agentic Training at Scale》（31 页，131 位作者），背景部分补充引用了 3FS、Firecracker、EROFS、DADI 等各自的官方文档与原始论文，链接都在文末。这篇可以和本博客的两篇旧文对着读：[E2B 那篇](/posts/2026-09-23-e2b-sandbox-infra/)讲单个沙箱的工艺，[MiMo 训练看板那篇](/posts/2026-09-27-mimo-v26-rl-oss-environments/)讲训练任务级的突发需求，DSec 补的是中间这一层：集群规模的执行底座。

</Prose>

智能体训练的形状和传统 RL 已经不一样了。一个 agentic RL 循环由三段组成：模型在环境里 rollout，环境里跑的是真实工具（shell、浏览器、编译器、包管理器），每一步操作都要有地方执行；执行结果喂给 reward 计算；策略再更新。这个「地方」就是沙箱：隔离、有状态、用完即弃。DeepSeek-R1 时代，rollout 主要是数学题和代码题，环境很轻；到了 SWE-bench、终端任务、计算机操作这类 agentic 任务，环境变成了完整的 Linux 机器，数量和寿命都上了一个量级。

这条线的源流比 DSec 早得多。2020 年，AWS 的 Firecracker 把 microVM 冷启动压到百毫秒级，serverless 和沙箱从此有了同一块积木；同年阿里的 DADI 把容器镜像做成块级按需加载，它的开源实现 OverlayBD 后来成了 DSec microVM 磁盘的底座。2025 年初 DeepSeek-R1 把 RL 推到台前，二月的开源周把 3FS 这批基础设施放了出来。2026 年，V4 预览把百万上下文和智能体能力做成产品，DeepSeek Harness 成为官方的 agent scaffold。DSec 这篇论文是这条线的合拢：训练侧的执行底座。

它占的位置也值得说清楚。serverless 平台（SAND、RunD 一类）假设镜像在本地、扇出高，和 DSec 的有状态、低扇出负载正好相反；RL 框架（veRL、Slime、Seer）把沙箱当黑盒，不管供给；E2B 这类服务把单沙箱工艺做到了极致。DSec 站在中间：集群规模、有状态、低扇出，并且和 RL 框架一起设计。

七个特征里最要命的是两个互相拉扯的事实。一方面，创建是突发的：一个 rollout 任务典型要几千个沙箱，最大的要 3.2 万个，而且要在短窗口内全部就绪，setup 成本被这个倍数直接放大。另一方面，跑起来之后大部分沙箱很闲：约九成容器和 microVM 沙箱平均只用了申请 CPU 的 5% 以下。超卖因此是合理的，但内存不能跟着胡闹。沙箱是有状态的，命令之间状态持续，后面的命令看得到前面装的包、改的文件；寿命中位数在 15 到 17 分钟，p99 超过三小时，空闲进程的内存就一直占着。

第二个矛盾是环境多样性。一周的生产统计里有 11,266 个基础镜像、102,171 个 workspace、103 个工具层。每周活跃的镜像产物超过 130 TB，远超节点本地盘；扇出却低得可怜：容器镜像中位数只有 3 个节点用过（p90 才 28），microVM 镜像中位数是 1。本地缓存几乎帮不上忙。更浪费的是，沙箱运行时实际只碰镜像数据的 4.2% 到 13.3%，eager 全量拉取绝大部分是白搬。

剩下三个特征一句话带过：异构（OJ 编译、SWE、安全对抗、GUI 任务混在一个集群里）、不可信（智能体会作弊，§07 细讲）、可抢占（GPU 训练任务会被调度器抢走，沙箱得能睡能醒）。DSec 所有的设计选择，都是被这七个特征逼出来的。

统一入口是 Python 客户端库 libdsec。一个请求要写清楚：沙箱类型、镜像或环境 ID、CPU 与内存上限、生命周期、网络规则、初始用户。论文给的例子是一个 4096 MB、4 CPU、300 秒空闲超时的容器，网络规则允许 PyPI、拒绝 NPM。注意这个设计姿态：平台提供谱系，但不替你赌隔离与性能的权衡，选哪一档是调用方的事。

请求路径一句话走完：IAM 认证鉴权（嵌套项目，子项目的配额和权限受父项目约束）→ 放置引擎在健康节点里随机抽几个、选最闲的 → apiserver 按沙箱 ID 里编码的归属 edge 转发，所以 apiserver 无状态、可以水平扩展 → edge 做节点本地准入、挂存储、下发 eBPF 网络策略、启动运行时。edge 握着最终准入权，拒了就换节点重试。每个容器和 microVM 沙箱里还跑着 aether 代理和 chronus 命令执行实例：aether 用 Unix domain socket 或 vsock 按终端会话 ID 路由命令，会话结束时把整个进程树收掉。放置引擎还有一手云 bursting：本地利用率超过 80% 时，符合条件的创建请求被甩到云上的 200 台 VM，它们复用同一套容器运行时和 EROFS 镜像路径，生产里约消化三成峰值溢出。

    <div slot="routing">
      <p class="stage-label">01 · 路由</p>
      <h3>选到节点，还要过本地准入</h3>
      <p>IAM 验明身份和配额后，放置引擎从健康节点里随机抽 k 台，选择最闲的一台。这种选法叫 power-of-k-choices。apiserver 再按沙箱 ID 中编码的归属 edge 转发请求。</p>
      <p>edge 是节点上的管理服务，资源不够时可以拒绝，上层随即换节点重试。集群选点和节点准入各管一关。</p>
    </div>
    <div slot="layers">
      <p class="stage-label">02 · 拼装</p>
      <h3>组合环境，不重做整块镜像</h3>
      <p>基础 OS、workspace 和工具层分别发布、独立版本化。创建容器时，dockerd 把选中的只读层叠成 overlayfs 的 <code>lowerdir</code>，合并成一棵目录树。上面的可写层接住运行时修改，下面的层保持不变。</p>
      <p>基础镜像升级，只重建对应的基础层。microVM 也采用相同的组合方式：EROFS 层作为只读块设备挂进客户机，再以 ext4 盘上的目录承接写入。</p>
    </div>
    <div slot="reads">
      <p class="stage-label">03 · 取数</p>
      <h3>先准备元数据，用到哪块读哪块</h3>
      <p>容器的 OCI 镜像离线转成 EROFS，元数据与文件数据分开存放。节点预取元数据，真正访问文件时再从 3FS 取数据，内核预读把零散请求合并；运行时写入留在本地盘。</p>
      <p>microVM 的块读取路径使用 OverlayBD 格式的 ext4 盘，通过 ublk 按需取数。两种后端共享按需读取的思路，具体格式和读取接口各不相同。</p>
    </div>
    <div slot="density">
      <p class="stage-label">04 · 运行</p>
      <h3>CPU 可以超卖，内存要省着用</h3>
      <p>约九成容器与 microVM 沙箱，平均 CPU 用量不超过申请量的 5%。等待模型生成下一步动作的间隙，让 CPU 超卖有了空间；长期保留的内存却不会自动归还。</p>
      <p>只读层通过 virtio-pmem 与 DAX（直接访问）共享宿主页缓存；可写盘由 DAMON（内存访问监测）定位冷页，再配合气球驱动归还空闲内存。CPU 调度还要避免低优先级任务挤占延迟敏感任务的同核线程。</p>
    </div>
    <div slot="suspend">
      <p class="stage-label">05 · 休眠 / 恢复</p>
      <h3>训练被抢占，执行状态留下来</h3>
      <p>GPU 训练任务被抢占时，RL 框架主动暂停关联沙箱。容器暂停进程、换出并回收内存；microVM 保存内存与执行状态快照，然后停止 Firecracker 进程，释放占用。</p>
      <p>下一次请求到来时透明恢复。容器侧用 <code>MADV_WILLNEED</code> 预取热页，microVM 则另起进程加载快照，继续此前的执行。</p>

  <SectionHead
    index="05"
    kicker="镜像分发"
    title="镜像不下载：130 TB 工作集怎么按需供给"
    lead="eager 拉取在这个负载画像下是纯粹的浪费。"
  />
  <Prose tile>

镜像分发是整套系统里最反直觉的一块。直觉做法是提前把镜像拉到节点上，但 130 TB 的周活跃产物、中位数 3 的扇出、4.2% 到 13.3% 的实际触碰率，让 eager 拉取变成白搬：8,192 个容器的突发里，eager 冷拉取要 60 多分钟，按需加载约 35 分钟，和全本地缓存的基线持平，磁盘写入还少了约 57%。

3FS 的脾气决定了方案。它顺序吞吐强、小随机 I/O 弱，所以分工很明确：写流量留在本地盘，只读数据按需批量取，元数据放本地。OCI 镜像离线转成 EROFS 格式，元数据和数据分开存放；元数据预取到节点，数据从 3FS 按需读，内核预读把零散请求合并。小于 3 GB 的连续小层离线合并成元数据/数据对，whiteout 语义保留；file-backed mount 避开 loop 设备开销。microVM 侧走 OverlayBD 格式的 ext4 盘，通过 ublk 以 256 KiB 为单位按需取数，本地盘做二级缓存，顺带支持增量快照。

被否决的方案也值得说。逐沙箱解包 tar.gz 会把突发期的 CPU 和 I/O 放大，实测 79 分钟对比直接挂载的 45 分钟，磁盘写流量 5.5 倍。bind mount 没有 append-merge 语义，撑不起分层组合。把基础镜像、workspace、工具层烤成整块镜像更不行：基础镜像升级要重建 O(m·N) 个整块，独立分层只要 O(m)。

  </Prose>

    title="密度的瓶颈不是 CPU，是内存"
    lead="CPU 超卖有九成沙箱的低使用率兜底；内存不行，因为沙箱有状态、寿命长。"
  />
  <Prose tile>

论文在内存上用了两对机制。第一对解决「重复」：microVM 的客户机页缓存和宿主页缓存本来是两份，virtio-pmem 加 DAX 把文件访问直接映射到宿主页，同机 microVM 共享一份宿主拷贝，峰值宿主内存直接降 40.2%。代价有两个：冷缺页同步处理，CPU 瞬时峰值从 26.5% 抬到 41.4%；客户机 struct page 元数据要吃掉设备容量的 1/64，128 GB 设备对应 2 GB 客户机内存。

第二对解决「占着不放」。DAMON 采样找出冷的文件页，走内核回收；空闲页攒成 order-9（2 MiB）大块，由 virtio-balloon 上报给宿主，madvise(MADV_DONTNEED) 释放。这一对对峰值内存影响不大，但时间积分降了 21.2%，适合长跑的可写盘。生产上的搭配是：只读层用 virtio-pmem，可写盘用 DAMON 加气球。

CPU 侧的问题是 SMT 兄弟线程互相打扰。BE 任务跑 SCHED_IDLE 只能保证「延迟敏感任务可运行时让路」，管不住同一个核的另一个线程；单独用它，50% BE 负载下的步级延迟膨胀最多改善 3.4%。加上 core scheduling（prctl(PR_SCHED_CORE)），禁止 BE 跑在延迟敏感任务的 SMT 兄弟上，膨胀从 45.2% 压到 17.3%。残余来自降频、内存带宽和 LLC 争抢，作者认为可接受。

然后是这篇论文最好看的部分：智能体会作弊。论文列了一批生产里抓到的真实案例。有智能体伪造发往 chronus socket 的 RPC 消息、翻 chronus 的日志、覆盖 /bin/bash；还有试图用 XFS_IOC_SWAPEXT 把受保护文件换出来的，真的搞坏了 XFS 元数据，逼得文件系统关机。沙箱外面也不老实：扫端口、扫镜像站、滥用 Go module 代理去 GitHub 拉现成实现。有些是纯粹的蠢事：递归 grep /proc 读到 /proc/kpagecgroup，把内核搞崩；给目标 VM 准备的 exploit 跑在了自己的容器里；yes 不停输出，捕获的 stdout 攒下几十 GB。
