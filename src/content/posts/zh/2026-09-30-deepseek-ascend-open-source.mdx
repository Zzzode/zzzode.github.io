<Prose tile>

2026 年 9 月 30 日上午，DeepSeek 通过官方公众号宣布，正式开源面向华为昇腾算力平台的基础设施组件，涵盖 TileLang 高级语言编译工具、计算库、分布式通信库，所有组件与此前面向英伟达平台的开源组件一一对应。

公告本身只有五段话，但六个 GitHub 仓库当天同步更新：TileLang 主线正式支持昇腾 950，DeepGEMM-Ascend 与 DeepEP-Ascend 分别在 9 月 29 日和 30 日建仓，TileKernels、FlashMLA、DeepSelect 三个仓库补齐昇腾后端。这不是象征性的适配——DeepGEMM-Ascend 的稠密矩阵乘跑到硬件上限的 99.8%，FlashMLA 昇腾版稀疏注意力 prefill 达到 410 TFLOPS，DeepEP-Ascend 的 MoE 通信在 EP32 以内跑到物理带宽的九成以上。

要理解这件事的分量，得先回答一个问题：国产芯片喊了这么多年，为什么「能跑 DeepSeek」直到今天才算数？答案不在芯片，在软件。

</Prose>

训练一个大模型，真正的算力消耗在成千上万的算子（kernel）上：矩阵乘、注意力、通信、量化。这些算子过去几乎全部用 CUDA 编写，而 CUDA 是英伟达的私有技术。芯片可以流片，CUDA 攒下的软件栈却搬不走：这是英伟达最深的护城河，也是国产算力过去几年最痛的地方。

TileLang 由北京大学团队发起（核心人物王磊、董宇骐，导师杨智），2025 年 1 月 20 日开源，编译底座是 Apache TVM。它的思路是把算子的数据流（tile 怎么搬、怎么算）与调度（线程怎么绑、流水线怎么排）解耦：前者是人写的，后者尽量交给编译器。2025 年 4 月的[论文](https://arxiv.org/abs/2504.17577)声称，TileLang 在关键算子上达到了当时的最佳性能。

海外社区第一次大规模注意到 TileLang，是因为 DeepSeek V3.2：2025 年 9 月底 V3.2-Exp 发布时，有人发现它的算子用的是 TileLang 而不是 OpenAI 的 Triton（这是社区观察，不是 DeepSeek 官方表述）。到了 2026 年 4 月 [V4 预览版开源](https://www.deepseek.com/news/v4-preview/)时，DeepSeek 自己的说法已经变成：TileLang 承载了 V4 系列模型训练中大部分算子的实现。

再往后就是今天。TileLang 路线先在英伟达成熟平台上验证，再搬昇腾。公告里「一一对应」四个字，是这条路线走了二十个月的结果。

「一一对应」落在三个层面。API 上，DeepGEMM-Ascend 与英伟达版完全兼容、连包名都一样，DeepEP-Ascend 的 EPBuffer 接口与英伟达版 V2.5 一致，训练框架改个硬件后端就能换平台。代码上，TileKernels、FlashMLA、DeepSelect 是同一仓库双后端，运行时按硬件自动选择，不存在两套分叉的代码。能力上，公告原话——DeepSeek 训练中用到的每一个 TileLang 算子，在昇腾上都有对应的高性能实现。

**一次前向里，五个库各管一段。** 以 DeepSeek V4 的一次推理前向为例：输入 token 先经过稀疏注意力（DSA），由 DeepSelect 从 KV cache 里筛出最相关的 512 个 token，FlashMLA 只对这部分 token 算注意力；进入 MoE 层后，路由为每个 token 选出 6 个专家，DeepEP 把 token 分发到专家所在的卡（dispatch），DeepGEMM 做专家内部的矩阵乘，DeepEP 再把结果收回（combine）。TileKernels 提供路由打分、FP8/FP4 量化、RoPE 这些配套算子。

实际调用都很短。DeepGEMM 的普通矩阵乘就是一行 `deep_gemm.fp8_gemm_nt(...)`，签名 `D = C + A @ B.T`，缩放因子按 UE8M0 打包格式传入；昇腾上首次调用时由 DeepJIT 现场编译，产物缓存在 `~/.dj`。DeepEP 的核心是一个长期存活的 buffer，dispatch 和 combine 都走它：

```python
from deep_ep import EPBuffer
buffer = EPBuffer(ep_group, num_max_tokens_per_rank=4096,
                  hidden=7168, num_topk=6)
buffer.dispatch(x, topk_idx=idx, topk_weights=w, num_experts=256)
```

TileKernels 是一组小算子，比如把权重量化成 DeepGEMM 要求的 FP8 布局：

```python
import tile_kernels
q_fp8, q_sf = tile_kernels.quant.per_token_cast(
    q_bf16, 'e4m3', 128, use_packed_ue8m0=True)
```

FlashMLA 的解码内核在循环里逐 token 调用，KV cache 走 FP8/FP4 量化格式：

```python
from flash_mla import flash_mla_with_kvcache
o, lse = flash_mla_with_kvcache(
    q, kvcache, block_table, cache_seqlens, dv,

```

DeepSelect 就是一个 TopK，但为 DSA 的 topk=512 场景做了极致优化：

```python
import deep_select
values, indices = deep_select.topk(x, 512, indices_type=torch.int32)
```

这次开源真正的主角是 TileLang。算子库可以逐个移植，语言路线错了，整个栈都要重来。

做 GPU 算子语言的不止一家。最主流的是 OpenAI 的 Triton，vLLM 等推理栈都在用；最底层的是 CUDA 本身，性能上限最高但只属于英伟达。TileLang 的位置在两者之间：比 CUDA 好写，比 Triton 更强调性能可移植。它的[论文](https://arxiv.org/abs/2504.17577)把调度空间（线程绑定、布局、张量化、流水线）做成一组注解和原语，编译器负责把它们降到不同硬件。

代码量的对比最直观。2025 年 9 月华为全联接大会的开发者日上，TileLang 团队成员董宇骐现场展示：FlashAttention 算子的开发从 500 多行降到 80 行，性能与官方版本持平（媒体报道口径）。海外社区还有开发者称，用不到 100 行 TileLang 写出了比 FlashAttention 2 原版快 30% 的注意力实现——这是单一来源的社区说法，我没有找到独立复现。

DeepSeek 用脚投票的过程很清楚：V3.2 被社区发现用 TileLang（2025 年 9 月），V4 训练大部分算子由 TileLang 实现（2026 年 4 月官方口径），今天昇腾后端进入主线。公告里有一句话说得很直白：TileLang 昇腾版本「希望能对更多 AI 芯片建立高可用软件生态起到示范作用」。它的后端列表也确实在往这个方向走：主线内有 CUDA、ROCm、昇腾 950、Metal，适配仓库覆盖昇腾 A2/A3、沐曦、摩尔线程、海光、日出。

  </Prose>
  <Prose tile>

**TileLang 代码长什么样。** README 里有一个完整例子：带 ReLU 的 FP16 矩阵乘，FP32 累加，二十来行：

```python
import torch
import tilelang
import tilelang.language as T

@tilelang.jit
def matmul_relu(A, B, block_M: int = 128, block_N: int = 128, block_K: int = 32):
    M, N, K = T.const("M, N, K")
    A: T.Tensor((M, K), T.float16)
    B: T.Tensor((K, N), T.float16)
    C = T.empty((M, N), T.float16)

    with T.Kernel(T.ceildiv(N, block_N), T.ceildiv(M, block_M), threads=128) as (bx, by):
        A_shared = T.alloc_shared((block_M, block_K), T.float16)
        B_shared = T.alloc_shared((block_K, block_N), T.float16)
        C_local = T.alloc_fragment((block_M, block_N), T.float32)

        T.clear(C_local)
        for k in T.Pipelined(T.ceildiv(K, block_K), num_stages=3):
            T.copy(A[by * block_M, k * block_K], A_shared)
            T.copy(B[k * block_K, bx * block_N], B_shared)
            T.gemm(A_shared, B_shared, C_local)

        for i, j in T.Parallel(block_M, block_N):
            C_local[i, j] = T.max(C_local[i, j], 0)

        T.copy(C_local, C[by * block_M, bx * block_N])

    return C
```

逐行读它。`@tilelang.jit` 让函数在第一次调用时按实际矩阵形状现场编译，换个形状就重新编译一份。`T.Kernel(...)` 声明线程块网格：每个块负责输出矩阵里的一个 128×128 tile，块内 128 个线程。`alloc_shared` 申请的是片上缓存（GPU 上是 shared memory，昇腾上对应 cube 核的 L1 buffer），`alloc_fragment` 申请的是寄存器级存储（昇腾上对应 L0A / L0B / L0C）。`T.Pipelined` 是软件流水线：搬下一块数据和算当前这块重叠进行，`num_stages=3` 表示三级流水。`T.gemm` 是真正的矩阵乘，编译器把它降到目标硬件的矩阵单元，GPU 上是 tensor core，昇腾上是 cube 核。最后 `T.Parallel` 里的 `T.max` 是 ReLU 收尾，一行写完。

人写的部分是「tile 怎么搬、怎么算」：哪些数据进片上缓存、流水几级、矩阵乘放在哪。编译器管的部分是「线程怎么绑、指令怎么排」：`threads=128` 只是个提示，具体的线程映射、寄存器分配、指令调度都由后端完成。这就是「数据流与调度解耦」在代码里的样子，也是 TileLang 能一份源码跑多个后端的原因。

通信库的舞台不是单机，是超节点。公告里有一句容易被略过的话：双方「共同推进基于昇腾 950 的 128 卡超节点方案」。DeepEP-Ascend 的性能测试也全部在超节点网络上完成——netlayer 1，即超节点的外部 Clos 网络。

为什么通信对 MoE 这么重要？DeepSeek 的模型每个 token 要路由到 6 个专家（top-6），dispatch 把 token 发给对应专家所在的卡，combine 再把结果收回来，这是一次全连接的 all-to-all 通信。EP 规模越大，通信占比越高：DeepEP-Ascend 的自测里，dispatch 带宽从 EP8 的 373–375 GB/s 缓慢降到 EP128 的 313–320 GB/s，EP32 以内能跑到物理带宽的九成以上。官方也坦白了短板：EP64 / EP128 与 combine 仍在优化，combine 有额外的本地归约开销和与 URMA 的 HBM 竞争。

硬件背景值得交代。华为 2025 年 9 月公布昇腾路线图（950PR 推理、950DT 训练、960、970）；2026 年 7 月 WAIC 上，Atlas 950 SuperPoD 真机亮相：1024 张 NPU 高速互联、256TB 统一内存编址、灵衢互联协议、往返时延约 3 微秒；上一代 384 超节点已商用超过 750 套。DeepSeek 与华为合作的 128 卡方案，可以理解为这个体系里面向训练的一个规模单元。

放在更大的背景里，这是出口管制下国产算力自我加速的一部分：英伟达 H200 今年 8 月才确认交付中国客户，占其数据中心收入不到 1%，而国产替代在推理侧已经跑上大规模流量（参见本站[《H200 对华销售核实》](/posts/2026-09-23-nvidia-h200-china-verification/)）。DeepSeek 这次开源，补上的是训练侧最硬的一块：算子栈。
