<Prose>

口径说明：本文依据两个库的官方 GitHub README 与 Gson 官方 User Guide（2026-09-23 核对；Gson 当前版本 2.14.0，官方声明处于**维护模式**）。YYModel 是 ibireme 的 YYKit 组件之一，库本身仅 5 个文件。这不是上手指南，而是一次跨生态的机制对比：同一个问题（JSON ↔ 对象）在两种运行时哲学下分别被怎样解决，又为什么双双被代码生成方案取代。

</Prose>

  <SectionHead
    kicker="01 · THE PROBLEM"
    title="前因：手写映射代码的痛，与「零侵入」的诱惑"
    lead="服务端返回 JSON，App 里要用的是对象。中间那段逐字段拷贝，是两个生态共同的无聊税。"
  />
  <Prose>

最朴素的 JSON 映射是手写的：解析成字典/树，然后 `user.name = json["name"]` 逐行搬运。嵌套结构、数组里的对象、缺字段、类型不符（服务端把数字返回成字符串是家常便饭）都要自己处理。模型一改，映射代码跟着改，漏一处就是运行时 bug。

两个库给出的承诺几乎一字不差：**定义普通类，剩下的交给库**。Gson 的设计目标明确写着——能序列化「你没有源码的、预先存在的对象」，不需要注解，不要求继承基类；YYModel 则把「非侵入（Non-intrusive）：无需继承任何基类」列为特性。要做到零侵入，唯一的办法是运行时自省（introspection）：库自己去问运行时「这个类有哪些字段、各是什么类型」，再自动生成映射。两条技术路线由此分岔，因为 **JVM 和 Objective-C runtime 愿意在运行时交出的类型信息，质量完全不同。**

  </Prose>
</Section>

Gson 官方 README 现在直白地写着两件事：**项目处于维护模式**；**不推荐在 Android 上使用**——理由正是它的立身之本：开放式反射与 Android 发布构建必经的缩减/优化/混淆流程（R8/ProGuard）天然冲突，字段可能被混淆或裁掉，线上崩溃由此而来；官方的推荐替代是 Kotlin 序列化（kotlinx.serialization），它在编译期生成适配器，还绕开了反射开销。对 Kotlin 的非空类型、默认参数构造器，Gson 也明确说不支持、可能产生「令人困惑的错误行为」。

YYModel 的处境是同一故事的 Swift 版本：Swift 引入 `Codable` 协议 + 编译器自动合成编解码代码，类型在编译期检查、与优化器和混淆器和平共处，Objective-C runtime 的消息魔法在纯 Swift 类型上根本无从施展。YYModel 至今仍是存量 ObjC 工程的高性价款，但新世界没有它的位置。
