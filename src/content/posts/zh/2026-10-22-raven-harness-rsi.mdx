<Section canvas id="purpose-and-goals">
  <SectionHead index="01" kicker="设计目的" title="让专业 Agent 的能力组合起来，完成跨领域的整项工作" />
  <Prose tile>

[Raven](https://github.com/EverMind-AI/Raven)希望用户能把整项工作的组织交给系统。用户提出目标后，由 Host Agent 选择执行者，安排任务的先后与交接，汇总交付物。Host 就是主控 Agent，可以调用 Raven 自带的专家，也可以指挥 Claude Code 等独立产品。

官方报告以开发 FPS 游戏为例。研究需求、编写玩法代码、制作视觉内容，直到集成测试和持续运行，每一步需要的工具与验收标准都不同。一个聊天模型能讨论这些工作，不等于同一套执行程序就能把它们做好。编码 Agent 与设计 Agent 各有一套适合自己领域的工作方法。

Harness 是模型周围的执行程序和规则：工具怎样使用，上下文怎样处理，技能、失败恢复和检查怎样接入。Raven 把“模型 + Harness”作为完整的调用单元。因此，接入 Claude Code，也就接入了它处理项目的那套方法。Host 负责安排它与其他执行者合作。

[官方报告引言](https://arxiv.org/html/2609.33439v1#S1)指出，专用 Harness 越做越复杂，靠人逐个适配模型和领域很难持续。即使各自做好了，不同 Harness 的输入、产物和执行方式也不一致，能力仍接不到一起。Raven 的编排与改进机制由此展开。

  </Prose>

  </RavenFigure>
  <Prose tile>

官方衡量组合价值时，比较的是同一资源预算下能可靠完成哪些任务。多加 Agent 也会增加规划和交接成本。专业能力互补，产物又能接上，才有机会完成单个 Agent 做不好的工作；交付结果仍需检验。

报告结尾还提出跨设备的长期助手：让不同环境中的 Raven 实例互相协调，延续任务与经验。记忆和开放协议都服务于这个方向，但跨设备进度同步等愿景尚不能算作当前能力。本文研究的是 `4315993` 源码快照，包版本为 `0.2.5`，官方仍标为 pre-alpha。

  </Prose>
</Section>

<Section canvas id="capability-map">
  <SectionHead index="02" kicker="能力全景" title="协作和 Harness 改进是主干，记忆与技能让成果留下来" />
  <Prose tile>

Raven 的主干能力可以分成两项：组织不同执行者完成当前任务，以及改进执行者以后怎样工作。记忆与技能把经验带到后续任务；主动触发与多种入口，则让系统能在配置允许的时机继续推进。

  </Prose>

    <div class="rv-transfer">Host 判断能否自己完成，还是需要组织专家</div>

  <Prose tile>

Raven 自带的专家各有侧重。Research 搜集资料并追踪来源，Code 修改项目并验证结果；Design 组织视觉交付，通常把 PPT 工作转给隐藏的 PPT Agent。Oncall 负责推进和观察长时间任务。它们在 Raven 的执行基础上增加领域工具与检查，外部 Agent 则保留自己的内部工作方式。

专家连上之后，交接仍得有人安排。历史也一样：存下来了，还要能找到并用于下一次工作，否则协调与补上下文的负担仍在人身上。

  </Prose>

<Section canvas id="collaboration-design">
  <SectionHead index="03" kicker="协作设计" title="Host 负责语义决策，调度器负责把任务图执行准确" />
  <Prose tile>

拆成哪些工作、交给谁、需要什么输入，以及结果是否要返工，这些决定需要理解任务，交给模型。节点引用是否合法、依赖有没有环、后端是否支持所需能力，则由程序检查。并发名额和结果存储也由程序管理，不靠模型记住执行到哪一步。

简单任务可以直接做，单个子任务用 `spawn`，多项相互依赖的工作用 `run_subagent_dag`。DAG 是有向无环图，节点表示一次 Agent 调用，边表示产物依赖。Host 提交图后，运行时校验并启动就绪节点。这里并没有强制前置的独立 Planner：默认 Planning 策略原样传递消息，模型可以在自己的工具循环里规划。

  </Prose>
  <RavenFigure id="raven-project-dag" title="开发一项功能：并行只发生在没有依赖的位置" caption="个人代码项目的教学设计。实现与文档使用不同文件范围；测试节点等待实现产物。是否采用这样的拆分，由 Host 结合项目决定。">
    <div class="rv-node rv-emphasis"><span class="rv-label">Host 的目标</span><h4>为导出功能补上边界处理，并给出可复核的交付</h4><p>先读项目约定，确定文件所有权、测试命令和禁止的外部动作。</p></div>
    <div class="rv-transfer">把任务与输入交给两个可以独立推进的节点</div>
    <div class="rv-grid">
      <div class="rv-node"><h4>实现节点 · Claude Code</h4><p>只改导出模块与对应测试；交出 diff、测试命令和实际输出。</p><p class="rv-small">输出 A：实现文件与验证记录。</p></div>
      <div class="rv-node"><h4>文档节点 · 另一位 Agent</h4><p>只读接口，起草使用说明；不写实现节点拥有的文件。</p><p class="rv-small">输出 B：文档草案与待确认项。</p></div>
    </div>
    <div class="rv-transfer">独立验收依赖实现；最终汇总依赖所有所需结果</div>
    <div class="rv-grid">
      <div class="rv-node"><h4>验收节点</h4><p>按验收条件检查 A，核对失败场景与测试证据；发现问题交回 Host。</p></div>
      <div class="rv-node"><h4>Host 汇总</h4><p>结合 A、B 和验收意见，决定继续、重规划或交付。需要发布时再触发重大授权。</p></div>
    </div>
  </RavenFigure>
  <Prose tile>

能读本机文件的后端可以接收输出路径，不能读的后端则需要在任务里拿到内容。节点提示词中的 `{{ api_audit.output }}` 引用已有输出，`depends_on` 声明前置节点。这样交接时，Host 不必重新复述所有内容，后续也能沿引用找到原始证据。

节点返回后，还要经过 verdict，即完成情况审查。失败进入异常处理时，Host 可以带着修正要求继续，也可以放弃或改用新节点重规划；已经完成的产物仍可引用。`instance` 表示子 Agent 的会话实例，同一实例的调用会串行。有确定先后要求时仍要写依赖，并行写代码也要另行划分文件所有权：系统不会自动创建隔离的 Git worktree。

交接可以自动推进，验收却要看具体检查了什么。当前实现中，普通节点的模型审查若超时或失败，会接受后端的正常返回。关键任务仍需真实测试和更严格的外部验收，发布权限也应独立管理。

  </Prose>
</Section>

<Section canvas id="self-improvement-design">
  <SectionHead index="04" kicker="改进设计" title="把工作方法拆成可替换策略，才能提出具体修改" />
  <Prose tile>

RSI 是 Recursive Self-Improvement，递归自我改进。Raven 主要研究怎样修改 Harness，执行模型可以保持不变。重试能改变这次输出；要影响后续任务，就得把上下文或工作策略的改动保存成可运行的新版本，再检验效果。

四个策略面给出了具体修改位置，外面的执行程序仍统一负责工具派发、事件、持久化和有边界的重试。改进器因此可以区分“工具根本没提供”与“工具提供了但执行前没检查”，针对原因修改，无需每次重写整个 Agent。

  </Prose>
  <RavenFigure id="raven-harness-seats" title="同一个模型周围，四个位置各管一种决定" caption="根据报告第 4 节与当前 Harness 模块整理。这里是执行责任划分；不表示默认每个模块都会额外调用一次模型。">
    <div class="rv-node rv-emphasis"><h4>模型与它的工作上下文</h4><p>模型提出回答或工具调用。Harness 控制它看到什么、可以做什么，以及结果如何进入下一步。</p></div>
    <div class="rv-transfer">改进器只改与失败原因有关的位置</div>
    <div class="rv-grid">
      <div class="rv-node"><span class="rv-label">Memory · 看见什么</span><h4>上下文与工作记忆</h4><p>组装材料、保留重要约束、在上下文压力下选择怎样缩减。</p><p class="rv-small">可改产物：引导文件、上下文策略或记忆接法。</p></div>
      <div class="rv-node"><span class="rv-label">Planning · 如何组织</span><h4>计划与协作程序</h4><p>提供逐步建议，或组织必须遵循依赖的多步工作。</p><p class="rv-small">可改产物：Playbook、技能与规划策略。</p></div>
      <div class="rv-node"><span class="rv-label">Capability · 能用什么</span><h4>工具与外部能力</h4><p>选择工具，通过 MCP 协议接入工具与资源，关闭不合适的入口或增加自检工具。</p><p class="rv-small">可改产物：工具配置、插件或新工具。</p></div>
      <div class="rv-node"><span class="rv-label">Action · 怎样执行</span><h4>响应与动作审查</h4><p>取得可用响应，在执行或交付前检查，必要时拒绝或要求重写。</p><p class="rv-small">可改产物：策略代码、工具关口与结果检查。</p></div>
    </div>
    <div class="rv-transfer">候选修改经过装配检查与任务评测后，才成为后续执行可用的版本</div>

### 改的是哪一层 Agent

在公开的 Curator 案例中，被修改的是受管理的 Raven Worker。生成物通过配置、home 文件、工具和回调等原有扩展点生效，不需要修改 `raven/` 核心源码。Evolver 的落点不同：它可以修改指定仓库中允许编辑的 Harness 源码，并把候选保存为 Git 提交。

把 Claude Code 通过 ACP 接进来，提供的是调用它的能力。不能由此推断 Curator 已经能够改写 Claude Code 自身的内部执行器。某项改进能不能实施，取决于那一层是否开放了对应的修改位置。[Curator 的扩展与装配说明](https://github.com/EverMind-AI/Raven/blob/4315993300e538ec954c79565cbc8585006c8053/experimental/docs/design.md)明确描述了它与 Raven Worker 的连接方式。

  <SectionHead index="07" kicker="接入实例" title="把 Claude Code 接入 Raven，再交给它一项项目任务" lead="下面给出界面与配置文件两条路径，连接的是完整 Claude Code Agent。" />

假设你有一个代码项目，想让 Raven 负责接活与监督，Claude Code 负责读文件、改代码和跑测试。需要分别准备 Host 的模型配置与子 Agent 的认证。Raven Host 能理解目标，不代表 Claude Code 已经能执行任务；Host 的 API Key 也不会变成 Claude Code 的账号。

### 准备 Raven 与 Claude 认证

macOS／Linux 的官方入门路径是：

```bash
curl -fsSL https://raven.evermind.ai/install.sh | bash
raven onboard
raven web
```

在 `onboard` 中配置主模型及需要的专业 Agent。普通 WebUI 默认地址为 `http://127.0.0.1:18792`；Docker 示例的 `18793` 是另一条启动路径。`raven status` 和 `raven doctor` 可以检查主服务和环境。

使用已有 Claude Code 登录时，先在日常终端启动一次 `claude`，按[官方认证说明](https://code.claude.com/docs/en/authentication)完成登录，并确认能正常回答。已有 API Key 或云平台配置的用户按原认证方式处理。Raven 常驻进程要能取得相应环境；在另一个终端里临时设置的变量，不会自行进入已经启动的服务。

Raven 的 `claude_code` 预设使用 ACP 适配器。当前快照固定的启动命令是：

```bash
npx -y @agentclientprotocol/claude-agent-acp@0.81.1
```

环境里需要可用的 `npx`，首次连接也可能下载适配器。按预设源码的说明，它运行 SDK 依赖所带的 CLI，不一定是 `PATH` 上那份 `claude`。已有登录是否可用，仍要通过 Raven 的真实任务检查确认。版本号对应本文快照，后续安装应核对当时的预设。

### 路径 B：直接合并配置

默认配置文件是 `~/.raven/config.json`；设置了 `RAVEN_HOME` 时，则使用该目录下的 `config.json`。下面是要合并到现有文件的片段。保留原来的 provider、主模型和其他 Agent，不要用这一段覆盖整个配置。`/absolute/path/to/project` 必须换成你的真实项目路径。

```json
{
  "subagents": {
    "agents": [
      {
        "name": "Claude Code",
        "preset": "claude_code",
        "kind": "acp",
        "enabled": true,
        "command": "npx -y @agentclientprotocol/claude-agent-acp@0.81.1",
        "cwd": "/absolute/path/to/project",
        "readyTimeoutMs": 120000,
        "timeout": 600
      }
    ]
  }
}
```

这是完整的 ACP 子 Agent 配置示例，无需再把 `ANTHROPIC_BASE_URL` 指向 Raven。调用方向是 Raven 启动并指挥 Claude Code，这条接入路径不提供 Claude 模型网关。

### 接入后，实际发什么任务

把会话工作目录设为项目后，先给 Host 这个任务：

> 请明确调用已连接的 Claude Code，检查当前项目 README、构建配置和测试入口，返回“如何启动、如何验证、缺什么前置条件”的报告。每项结论给文件位置。只读，不改文件，不提交，不推送。由你检查它的结果并汇总。

要看它是否真的读了项目。子任务中应有 Claude Code 的执行记录，报告也应指向正确的文件位置；一句“连接正常”不足以验证认证、目录和文件读取都可用。

接着再给一个范围明确的修改任务。下面是教学示例，文件名要换成项目里的真实路径：

> 请把导出模块的空数据处理交给 Claude Code 实现，只允许修改 `src/export/` 和 `tests/export/`。开始前先读取项目约定并确定测试命令；完成后交出 diff、测试命令、退出结果和未解决问题。你负责审查，发现问题直接继续或重规划，不需要我搬运意见。不要提交、推送或发布。

如果启用了 Raven-Code，可以让它独立审查实现，自己核对测试和边界条件。审查意见交回 Host，由它决定返工并推动后续执行。是否合格看文件和验证结果，模型说“完成”还不够。

### brief_action.py 怎样改变写文件这一步

公开案例里，写需求单的 Agent 已经收到提示词要求，却仍把内部调研备注写进需求单。PPT Agent 又沿用需求单内容，错误就进入最终方案。Curator 因此生成 `brief_action.py`，把审核接到需求单写盘前，也检查最后回答交出的需求单正文。检查从“模型应该记住的要求”变成了实际执行路径。

### 看一段真正生成的检查

入职时生成的 `hl_action.py` 用下面的判断限制提问数量。节选保留原意，完整 diff 在公开的入职记录中。

```python
asked = text.count("？") + text.count("?")
if asked > 2:
    problems.append(f"一条消息里问了 {asked} 个问题，每条消息最多问两个问题")
```

检查已经接进执行路径，但它只能数问号，判断不了一句话里实际问了几个问题。用了 Python，也仍有这种覆盖范围的限制。

第二轮后的门票检查更接近业务规则。下面是[案例提供的生成代码节选](https://github.com/EverMind-AI/Raven/blob/4315993300e538ec954c79565cbc8585006c8053/experimental/simulation/cases/s0925c/README.md)，不是可独立运行的完整程序：

```python
rules = _rules(research, free)
results = [(snippet, [pred(a) for a in ages]) for snippet, pred in rules]
if computable and counts_set == {claimed}:
    continue
```

代码从调研中取出可计算的年龄规则，对每个孩子求值，再与文稿声称的人数比较。一致才放行。第一轮加审核，第二轮补规则，到第三轮才看到新条件实际拦住错误。反馈由此变成了以后每次执行都能经过的检查。

<Section canvas id="offline-evolver">
  <SectionHead index="10" kicker="离线进化" title="基因库保留不同改法，评测决定什么值得继续" />
  <Prose tile>

[官方报告第 4 节](https://arxiv.org/html/2609.33439v1#S4)把候选组织成 Harness Gene Bank。它按照改动类型与失败类型保存经过评价的完整 Harness，支持从档案中取出机制重新组合；组合后仍要单独评测，不能把两项收益直接相加。仓库里的 Evolver 提供一条独立执行路径：固定基准任务与评分，让模型诊断失败、设计补丁，再把候选 Harness 放到相同条件下评测。它是独立工具，使用 Raven 作为库；正常的 Host 运行时不导入它。当前统一启动器只注册了 AppWorld，仓库中出现其他评测目录不代表它们也能直接作为启动目标。

先固定根 Git 提交和被测 Agent 的模型配置，跑出冷启动基线。模型读取训练任务的失败轨迹，提出候选补丁；程序记录候选为真实的子提交。默认先用每题 `K=1` 次的低成本筛选，幸存候选再用全训练集 `K=3` 次确认。`K` 表示每项任务尝试的次数，冒烟配置可以覆盖这些默认值。

  </Prose>

几道门槛检查的东西不同。Gate-f 记录基础设施污染，残留故障仍留在固定分母里，按未通过计算。Gate-b 用 activation beacon（执行标记）检查候选代码是否执行，没有埋点数据时可能不起作用；Gate2 则计算候选与基线的成对收益。Beacon 只能证明带标记的代码跑过，不能单独证明收益由它造成。

[实现映射文档](https://github.com/EverMind-AI/Raven/blob/4315993300e538ec954c79565cbc8585006c8053/docs-site/docs/self-evolution-map.md)还明确区分“被选作继续探索的版本”和 `credited_2sigma` 统计信用。训练平均分高一些可以推动探索，不等于已经证明具有统计显著性。候选被 promoted，也不等于已经合并到你的工作分支或部署。

一旦准备好真实任务、独立 AppWorld 环境和配置文件，官方操作顺序是：

```bash
uv run python -m evolver check --config /path/to/my_run.yaml
uv run python -m evolver run --config /path/to/my_run.yaml --smoke
uv run python -m evolver status --config /path/to/my_run.yaml --smoke
uv run python -m evolver run --config /path/to/my_run.yaml
```

运行前要准备好配置，固定 `repo_root`、`base_sha`、模型与任务划分；完整字段见[官方运行说明](https://github.com/EverMind-AI/Raven/blob/4315993300e538ec954c79565cbc8585006c8053/docs-site/docs/evolver.md)。`check` 默认就可能发出小型真实模型探测，smoke 也可能调用模型、执行候选代码并生成提交。反复执行被测 Agent 是主要开销，限制轮次并不能保证费用不超出某个金额。

完成的试验与轮次可以从产物恢复，封存测试集的结果通常不进入决策路径。`finalize --yes` 会结束实验并解封，不是暂停按钮；之后继续针对已看到的测试结果改版本，会破坏这次留出评测的意义。

### 为什么现在不宜把它当作长期依赖

当前文档已注明，`evolver/` 计划随相关旧树退役，仍待确认。公开状态记录了测试和真实 AppWorld 冒烟，尚未证明完成真实大规模多轮与封存测试保留率验证。部分算法文件也没有接入主流程。README 中的宣传图和展示项目不提供这些缺失的验证。

候选代码会以评测进程的权限执行，路径白名单和评分代码的不可改约束也没有构成完整的操作系统沙箱。若要研究这条路线，应在隔离环境中跑实验，并审查候选 diff。对日常个人项目，更直接的起点是先把任务调度和验收做稳。

### 两个尤其容易被误当成保证的开关

`background: true` 表示工具尽早返回 run ID，结果随后通知会话；它没有承诺宿主进程结束后继续运行。重启后从历史看到 `interrupted`，说明记录恢复了，任务并没有自动恢复执行。重新派发前要检查已经写出的文件或外部副作用。

`confirm: true` 请求先批准整张图。当前实现没有接入 ask channel 时，会记录提示并继续未经确认的调度。它不能独自保护无人值守的发布操作。要做到“只有重大决策需要人”，应让日常任务在明确授权内自动完成，同时让重大动作在缺少批准时确实无法取得执行权限。

权限本身也有边界。`smart` 模式用模型审查 ask 级动作，失败会升级；`full` 处理的是省去询问，仍保留 deny。无响应者的单次 CLI 不能完成人工审批，相关拒绝会反映到退出状态。外部 Agent 内部的工具权限还要单独配置，不能只看 Host 的模式。

可以从只读研究与审查开始，再开放有文件边界的开发任务。测试、失败恢复和预算观察都留下证据后，再扩大无人值守范围。RSI 优先处理反复出现、能核查结果的问题，也便于判断这些新增机制究竟省了多少人的工作。
