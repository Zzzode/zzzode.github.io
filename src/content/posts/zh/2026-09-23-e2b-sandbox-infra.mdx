<Prose>

先交代信息来源。本文事实来自 E2B 官方文档（docs.e2b.dev，2026-09-23 核对）、[e2b-dev/E2B](https://github.com/e2b-dev/E2B) 的 SDK 说明，以及 Apache-2.0 许可的 [E2B Runtime 基础设施仓库](https://github.com/e2b-dev/infra)。产品额度随版本变化，具体数字以官方计费页为准。这篇可以和本博客的 MiMo 训练看板那篇对着读：那边一次大跑要同时调动数万个沙箱，这篇讲的是单个沙箱怎么造。

</Prose>

<Section id="backdrop">
  <SectionHead
    kicker="01 · THE BACKDROP"
    title="前因：代码解释器不够用了，智能体要的是一整台机器"
    lead="「在隔离环境里跑 AI 写的代码」这件事早就存在，智能体把要求拉高了不止一档。"
  />
  <Prose>

**第一代：代码解释器。** ChatGPT 的 Code Interpreter 让「模型写 Python、后端在容器里跑、返回图表」成为标配。它的执行单元是一个被管起来的解释器内核（kernel）：语言基本固定、生命周期短、交互面是 notebook 式的单元格。它证明了隔离执行是杀手级功能，但也把能力圈在数据分析里。

**第二代：计算机操作智能体。** 当智能体要自己 `pip install`、起服务器、点浏览器、跑构建、写多文件项目时，解释器内核不够用了——它需要的是一台**完整的 Linux 机器**：任意二进制、常驻进程、多端口、文件系统状态、可能还要跑几十分钟。而这台机器执行的是**不可信代码**（模型生成、甚至被网页内容注入），所以还必须强隔离、快创建、用完即弃。

这三个要求放在一起是矛盾的：容器够快但隔离共享宿主内核，传统虚拟机够安全但启动要几十秒，两者都不为「每个会话一台、按需暂停、随时分叉」设计。E2B 的答案是 AWS 开源的 [Firecracker microVM](https://firecracker-microvm.github.io/)——就是支撑 AWS Lambda 与 Fargate 的那套轻量虚拟机技术——加上一套以快照为中心的调度层。

  </Prose>
</Section>

  <Prose>

用法只有四行：`Sandbox.create()` 起一台机器，`sandbox.commands.run(...)` 执行命令，`files.write/read` 操作文件，结束自动或手动释放。JavaScript/TypeScript 与 Python 两套 SDK 背后是同一个运行时。开源的 Runtime 仓库包含控制面 API、每台宿主机上的 orchestrator、每个 VM 内部的 envd、边缘路由与模板构建器——公有云、企业专属部署和单机评估包（Embed）跑的是同一套 Go 代码。

  </Prose>
</Section>

  <Prose>

E2B 的隔离不是只靠 VM 这一层：每个沙箱有自己的 cgroup 与网络命名空间，每沙箱一条 nftables 出网防火墙，并在 SNI/Host 层做域名允许与拒绝清单。架构上还坚持**控制面与数据面分离**——API 只决定沙箱调度到哪台机器、记录它存在；每台宿主机上的 orchestrator 才掌握 Firecracker 进程、块设备与 cgroup；沙箱流量从边缘直达节点，从不经过控制面 API。这样即使控制面出问题，正在跑的沙箱流量也不受影响。

  </Prose>
</Section>
