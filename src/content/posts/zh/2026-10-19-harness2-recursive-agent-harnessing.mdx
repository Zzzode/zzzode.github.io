<Section canvas id="motivation">
  <SectionHead index="01" kicker="问题来由" title="模型会做，执行时却可能漏做" lead="从改一份答案，走到改产生答案的工作流程。" />
  <Prose tile>

让智能体整理一份预算，它可能知道怎么计算，却没有核对不同文件里的数字；让它生成文档，它也可能在写出文件后直接结束，没有重新打开检查。这样的失败与执行流程有关。增加模型知识，未必能直接修好这次漏检。

Harness 是围绕模型运行的一套设施，包括提示词、工具、记忆和任务编排。可以把它理解为智能体的执行环境与工作规程。Harness² 允许另一个负责改进的智能体编辑这些文件，再用修改后的配置重做当前任务。模型参数保持不变，变化发生在模型周围。

这条思路有前序工作。[Self-Refine](https://arxiv.org/abs/2303.17651)让模型给自己的输出提意见，再反复修改输出；[Reflexion](https://arxiv.org/abs/2303.11366)把任务反馈写成语言形式的反思，保存在记忆中，帮助后续尝试。Harness² 把可修改的对象扩展到可执行的配置文件，并追踪一次修改怎样改变执行行为。

现实工作给这种修改带来两个困难。许多任务没有现成的标准答案，编辑器拿不到一个可信分数来决定该保留什么。任务切换也会出问题：为某份合同加入的规则，放到下一份预算表里可能毫无帮助，甚至误导执行。

2026-10-09 的[论文](https://arxiv.org/html/2610.14224v1)由 Ruiyao Xu 等作者发表，署名机构包括 Google Cloud AI Research 和 Northwestern University。量子位的原文介绍了其双层递归和主要成绩。这里进一步核对论文附录与固定版本源码，把操作方法、算力成本以及判断失误也展开说明。开源仓库位于 Google Research 名下，但 README 明确说它不是获得官方产品支持的 Google 产品。

  </Prose>

编辑器要根据故障选择合适的组件，避免为简单问题增加复杂流程。论文提示词要求把每项修改对应到轨迹中的具体时刻；没有证据时可以保持原配置。创建技能还必须提供触发说明，引用的脚本也要一起交付。源码会检查文件结构等条件，非法提案重试后仍失败，就回退到进入该阶段时的配置。通过这些检查，只说明配置可以进入后续执行，不能证明它会做对任务。

<Section canvas id="behavioral-evidence">
  <SectionHead index="04" kicker="判断依据" title="没有标准答案，怎样决定修改值得留下" />
  <Prose tile>

Behavioral Contrast 可以译为行为对比。它比较修改前后的执行，寻找目标问题有没有变化。例如原来只写文件，候选增加重开检查，并在这一步发现缺失页；这比模型说“新答案更专业”更容易核对，因为能指出一次具体动作及其结果。

参考执行和候选执行使用同一个任务，并尽量保持模型与环境配置一致，是为了减少比较中的干扰。但模型执行仍有随机性，一次试跑里做得更好，可能包含偶然因素。两个候选如果由相似模型根据相同材料提出，也可能共享同一个错误前提。候选意见一致，并不构成独立证明。

  </Prose>
  <MechanismSequence steps={[
    { tag: '证据边界', title: '把“这项修改有帮助”与“整个结果正确”分开', body: 'Composer 要为保留、修订或放弃的决定指出轨迹依据。能观察到复查步骤修复了缺项，就有理由保留该步骤；文档中其他数字是否正确、结论是否可靠，还需要另外检查。图中是解释判断方式的教学例子，没有对应的实测分数。' },
  ]}>
    <Fragment slot="frame-0" set:html={evidence} />
    <p slot="caption-0">行为对比是改进信号，不能替代外部验收，也不能证明修改对新任务必然有效。</p>
  </MechanismSequence>
  <Prose tile>

这也是论文“没有 ground-truth feedback”的准确含义：改进阶段不依靠标准答案、评分规则或评委打分。它仍依靠模型判断，而且实验结束后照常使用基准评委评分，才能测量有没有进步。“改进不看分数”和“实验没有评估”是两回事。

源码会在构建编辑上下文时过滤评委结果，但边界只在本地文件层面。官方[实验指南](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/docs/EXPERIMENTS.md#web-access)记录，发布版的一次 Codex 验证运行曾自行从网上下载 JobBench 评分规则。若执行器可以联网，公开规则仍可能绕过本地过滤进入上下文。复现时必须单独控制网络，否则“没有标准答案”的实验前提可能被破坏。这条发布版记录并不能据此证明论文实验已经受到污染。

  </Prose>

<Section canvas id="across-tasks">
  <SectionHead index="05" kicker="跨任务积累" title="下一次从基础配置开始，但不必忘记上次学到的修改方法" />
  <Prose tile>

Harness² 区分执行配置和改进配置。执行配置决定当前任务怎么做；改进配置给负责编辑的智能体提供经验，帮助它决定怎么改。标题里的第二层递归，发生在后者。

一次任务结束后，Experience Reflector（经验反思器）回看完整的改进记录，包括候选试过什么、执行有什么差异，以及最后怎样取舍。经验库保存被采用的完整配置文件树，并配一份 `EXPERIENCE.md`。它记录适用情形、修改经验和支撑证据；索引用来帮助后续会话按需找到相关条目。没有足够证据时，可以不写新条目。

  </Prose>
  <MechanismSequence steps={[
    { tag: '两个任务之间', title: '配置可以被借鉴，不会自动整套继承', body: '任务 A 的配置进入经验库，供任务 B 的编辑器阅读。B 的执行仍从共同基础 H0 开始；编辑器可以复制或改写旧组件，但必须核对 B 的文件、字段和约束。这样保留了可复用的做法，也减少把 A 的具体事实直接带到 B 的机会。' },
  ]}>
    <Fragment slot="frame-0" set:html={library} />
    <p slot="caption-0">模型参数与阶段指令保持固定，持续变化的是改进经验库。当前开源实现按领域组织库，并隔离不同实验配置。</p>
  </MechanismSequence>
  <Prose tile>

比如，一次任务发现两份表的岗位名称不同。“先核对名称映射，再连接数据”可能值得复用；“这份文件中的 HR 对应 HR Manager”则是当前工作区的事实。后者可以随原配置保存为案例，但在新任务里必须重新验证。旧案例里的值如果未经核对就沿用，经验库也会传播错误。

所以，这里的递归自我改进有一个具体范围：经验库改变了下一次提出和评估修改时能参考的材料。模型权重、阶段算法及其固定提示词，并没有随着每个任务自行重新训练或任意重写。长期库如何去重、清理过时经验，论文仍把它列为后续方向。

  </Prose>
</Section>

<Section canvas id="local-demo">
  <SectionHead index="06" kicker="逐步演进" title="沿着两轮执行，逐个查看 RSI 改了什么" lead="把初始配置、文件差异、执行结果和下次任务的上下文放在一起看。" />
  <Prose tile>

RSI 是 Recursive Self-Improvement，即递归自我改进。在 Harness² 中，需要追踪两个状态：当前任务的执行配置 H，以及跨任务保留的改进经验库 R。H 决定任务怎么执行，R 影响编辑器下一次根据什么材料提出修改。模型参数始终不变。

下面沿本文已经运行的官方 `harness2-demo --k 2` 查看真实文件。H0、H1、H2 是本文给执行配置快照起的名字，分别对应初始配置、第一轮组合 `c1`、第二轮组合 `c2`；R0、R1 表示空经验库和写入首条经验后的库。它们用于说明状态，不是项目命令。

这是一条真实运行的框架流程，但编辑器是预设程序。文件变化可以直接核对，模型自主发现问题的能力则没有在这个演示中受测。尤其要留意第二轮：这里 H2 与 H1 完全相同，并没有再进步一次。

### 起点：H0 有什么问题

任务 A 的要求是累加账本中的全部带符号金额。输入依次为 `100.25`、`-20.10` 和 `5.00`。初始 `scripts/summarize.py` 却带有正数过滤：

```python
# H0: excerpts from scripts/summarize.py
amounts = [Decimal(row['amount']) for row in csv.DictReader(source)]
total = sum((amount for amount in amounts if amount > 0), Decimal(0))
```

这会忽略负数。两次参考执行 `base1`、`base2` 都得到 `Total: 105.25`。参考执行的作用是暴露当前配置的行为；它不能充当正确答案。

### 第一轮：修改文件，分别重跑，再组合

演示里的 `DemoProposer.call()` 不会思考原因，而是对文件执行字符串替换，删除 ` if amount > 0`。通用候选 `inv1` 和领域候选 `dom1` 都做同一项改动。这次演示没有体现真实模型版本中两类编辑器的专业分工。

```diff
--- H0/scripts/summarize.py
+++ H1/scripts/summarize.py
-total = sum((amount for amount in amounts if amount > 0), Decimal(0))
+total = sum((amount for amount in amounts), Decimal(0))
```

最小步骤 `k=1` 有一条参考执行、两个候选执行，以及一条组合后的执行。提高 `k`，可以选并行递归或顺序递归。并行递归探索更多候选；顺序递归则让下一轮沿着上一轮的配置继续修订。

并行模式先收集 `k` 条参考执行，提出并试跑 `k` 个通用候选和 `k` 个领域候选，再启动 `k` 次独立组合。每个组合会话都能读完整候选池，并执行自己的组合结果。当前实现做一次这样的群体更新，`k=5` 不表示五层连续自我重写。

顺序模式同样有 `k` 条初始参考执行，但会串起 `k` 轮改进。后一轮看到当前配置和累积证据，可以保留早先修改，也可以撤回走偏的部分。每轮仍有通用、领域两个候选及组合执行。

固定版本的[选择池实现](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/selection.py)只把各次组合的结果交给最终选择器，参考执行与未经组合的候选不会直接参选。组合阶段可以保留当前配置，这与最终选择阶段的候选范围要分开理解。

<Section canvas id="model-backed-use">

开源版是一套实验框架，提供 JobBench、LAB 和 WorkBuddy-Bench 三类适配器，默认执行器为 OpenCode。接入其他任务，需要提供任务材料、执行方式和产物读取等适配，无法只给现有编程会话加个开关，就获得整套跨任务改进能力。

模型实跑按官方安装指南准备 Linux、Node.js 20+、Google Cloud CLI；LAB 还需要 Pandoc 和 Poppler，WorkBuddy 需要 Docker。下面沿官方 Vertex AI 路线，模型必须是你账号实际有权调用的标识。

README 要求复制 `.env.example`，但本文固定的提交没有这份文件。可以直接新建 `.env`，使用源码读取的变量；下列全部是待替换的教学占位符，不是可用账号或经过验证的模型名称。

```dotenv
GOOGLE_CLOUD_PROJECT=REPLACE_WITH_YOUR_PROJECT
GOOGLE_CLOUD_LOCATION=global
HARNESS2_SOLVER_MODEL=google-vertex/REPLACE_WITH_EXECUTOR_MODEL_ID
HARNESS2_IMPROVER_MODEL=google-vertex/REPLACE_WITH_IMPROVER_MODEL_ID
HARNESS2_JUDGE_MODEL=REPLACE_WITH_BARE_JUDGE_MODEL_ID
```

执行器和改进器使用 OpenCode 的 `provider/model` 格式，评委变量使用不带 provider 前缀的模型标识。`HARNESS2_IMPROVER_MODEL` 未设置时默认沿用执行模型。环境变量优先于 `.env`，排查“改了配置却不生效”时要一起检查。凭据与 `.env` 留在本地，不要加入版本库。

准备好账号权限后登录，再安装 LAB 并检查：

```bash
gcloud auth application-default login
harness2-setup lab
harness2-check --bench lab

export HARNESS2_RUNS_DIR=runs/lab-first-task
harness2 --bench lab --k 1 --mode parallel \
  --only-domains antitrust-competition --max-tasks 1 --dry-run
```

`--dry-run` 预览任务选择，不调用模型。`harness2-check` 检查依赖、凭据和配置，也不验证模型实际上能否调用；真实可用性要等第一次模型请求才知道。确认选择之后，移除 `--dry-run` 执行，再评分和出报告：

```bash
harness2 --bench lab --k 1 --mode parallel \
  --only-domains antitrust-competition --max-tasks 1
harness2-judge --bench lab --k 1 --mode parallel
harness2-report --bench lab --k 1 --mode parallel
```

这里先限制一个领域很有必要：`--max-tasks 1` 表示每个领域最多一项，单独使用并不是全局只跑一次。运行、评分与报告须对应同一个基准、执行器、模式、预算及种子；使用相同的输出根目录查看此次运行。想比较预算或更换模型时，另设 `HARNESS2_RUNS_DIR`，避免续跑结果混淆。本文没有执行这些付费模型命令。

### 使用 Codex 执行器

Codex 路线增加了模型接口适配：它连接 Responses API 端点；仓库内的 `harness2-bridge` 用本地 LiteLLM 服务把 Vertex Gemini 暴露成该接口。这层桥接解决模型通信，Harness² 的提案、试跑和经验库仍在外层运行。

```bash
uv pip install -e '.[render,bridge]'
harness2-bridge
```

保持 bridge 在单独终端运行，把它打印的 `HARNESS2_CODEX_*` 设置加到本地 `.env`。随后在另一终端执行：

```bash
harness2-setup lab --substrate cx
harness2-check --bench lab --substrate cx
harness2 --bench lab --substrate cx --k 1 --mode parallel \
  --only-domains antitrust-competition --max-tasks 1
harness2-judge --bench lab --substrate cx --k 1 --mode parallel
harness2-report --bench lab --substrate cx --k 1 --mode parallel
```

使用其他 Responses API 端点时，按[设置文档](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/docs/SETUP.md#codex-executor)配置 `HARNESS2_CODEX_BASE_URL`、`HARNESS2_CODEX_API_KEY` 和 `HARNESS2_CODEX_MODEL`。修改端点或模型后要重跑 setup，因为安装过程会把它们写进隔离的 Codex 配置。

开源执行器默认不限制网络，Codex 的沙箱也被关闭。真正做基准实验时，按官方指南在执行器网络层阻止获取公开答案或评分规则的渠道，同时保留任务需要的模型通信。这项措施与安装阶段下载依赖的网络需求不同。它也说明实跑应放在专用环境，先检查候选脚本和插件的执行权限。

  </Prose>
</Section>

  <Prose tile>

Harness² 的可借鉴之处，是把修改执行流程这件事留下完整记录：问题在哪次轨迹中出现，候选改了什么，重跑发生什么变化，以及这条经验下次何时适用。经验库同时保存可执行组件，后续智能体可以真正借用它们。

这套判断也会失误。论文附录 E.6 展示过选择器放弃得分 95 的候选，选中得分 55 的结果；分数是事后评估，选择当时并不知道。其他失败来自错误前提被多个候选共同采用，或一次执行的随机波动。增加递归预算不能自动修好这些判断。

在自己的系统里试验时，先挑输入固定、能够重跑的工作，并确保产物有办法验收。隔离候选工作区，保留基础执行作为对照，再统计完整调用量和人工验收结果。对于会直接发邮件、改线上数据的任务，需要先把可重复的试验环境建好：Harness² 会多次执行当前任务，任务本身的外部副作用不会因为换了配置就自动消失。这是由重跑机制得到的工程建议，不是本文已经验证的产品保障。

复现论文还要固定任务划分。发布版文档说 LAB 完整任务流有 1,143 项，论文主表却只使用 100 项保留测试任务；不加选择地运行默认全集，不会自然得到相同口径。库是否从空开始、任务顺序和联网条件都需要记录。框架默认的种子控制任务排列，不控制模型采样。

开源代码采用 Apache 2.0 许可证，第三方基准保留各自许可。未来的自动预算分配、经验库整理，仍属于论文提出的研究方向。当前材料支持的结论是：在被测职业任务与配置上，冻结模型也可以通过改进执行流程提高成绩，并让修改经验帮助后续任务。要判断它是否值得加入自己的系统，还得把额外推理与检查成本一同算进去。
