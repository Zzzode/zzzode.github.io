    title="前因：Agent 产品的共同点是「常驻」与「动手」"

  <Prose tile>

2025–2026 年的 Agent 产品有一个共同的位移：AI 不再是网页里一个用完即走的对话框，而是**长期在线、有身份、能被 @、能替你操作真实系统的行动者**。本博客 [Claude Code 架构解剖](/posts/2026-09-23-claude-code-architecture/)里讲过，能力 = 模型 + harness（外壳：工具、执行循环、记忆、技能）；Grok Bot 与 OpenClaw 的争论本质上是两种 harness 形态之争，模型反而是可替换部件。

两者共享四个前提：都能真正动手（调工具、操作软件、跑完多步任务）；都以「常驻同事/管家」为交互隐喻；都接入日常 IM 而不是另开一个 App；都承认能力沉淀靠外壳（skill、routine、记忆）而不是单靠更大的模型。分岔从下一个问题开始：**这个行动者住在谁的机器上，替谁承担风险？**

  <SectionHead
    index="05"
    kicker="可信计算基"
    title="真正的分野：谁是可信计算基（TCB）"
    lead="两种形态最深的差异不是功能表，而是「安全由谁兜底」的答案相反。"
  />
  <Prose tile>

OpenClaw 官方文档把话说得很重：**架构决定 agent「能」做什么，远早于策略决定它「可以」做什么。** 它的答案是信任最小化：Gateway 持有长期授权但不直接执行，执行移到沙箱/节点/一次性云机，用生命周期独立的受限凭据；拒绝必须是结构性的（代码里写死的绑定规则与 fail-closed 审批），而不是在系统提示词里恳求模型「请不要这么做」。配套还有默认拒绝的入站访问、凭据归属隔离、schema 版本化状态与防破坏升级。代价是默认沙箱关闭、一切需要你自己配对——自由与责任在同一个地方。

Grok Bot 的答案是信任转移：你把登录态交给 xAI 云端的虚拟机，换零装配、长程在线与多 bot 协作；安全与治理由供应商的多租户隔离、审批回环与企业身份集成（SAML/OIDC）兜底。这对「自己没有运维能力、但相信供应商」的团队是巨大解放；对数据不能出域、需要审计每一步凭据使用的组织，则是结构性障碍。这不是「谁更先进」的问题，而是**可信计算基的位置**：前者把 TCB 放在你自己的机器与配置上，后者放在 xAI 的云上。

  </Prose>
</Section>
