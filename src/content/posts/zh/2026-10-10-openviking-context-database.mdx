<Prose>

你在 Claude Code 里把一个项目做到一半，额度用完了，切到 Codex 继续。新 Agent 面对的是一段简短的 handoff 说明和一堆代码文件。之前聊过的背景、试过的方案、排查过的坑，全都丢了。你不得不重新解释一遍，等着新 Agent 从头再来。

这不是模型不够聪明的问题。是上下文没有跟着任务走。

OpenViking 想解决的就是这个问题。它是字节跳动 Viking 团队开源的 Agent 上下文数据库，把知识、记忆和技能组织成一个 `viking://` 虚拟文件系统。豆包、Trae、Codex、Claude Code 都可以接到同一个 OpenViking 上读写。Agent 换了，上下文还在。

</Prose>

    <Prose tile>

2024 年底 Anthropic 发布 MCP（Model Context Protocol），解决了 Agent 标准化调用工具的问题。但 MCP 管的是"手"，不管"脑"。Agent 能调工具了，可它的记忆仍然锁在各自的会话窗口里。

2025 年 Coding Agent 爆发。Claude Code、Codex、Cursor、Trae、豆包各占山头，用户在不同 Agent 之间切换的原因五花八门：额度、环境、合规、工具适配、阶段分工。不管原因是什么，切换的代价都一样：上下文断了。项目做到哪了、为什么选这个方案、哪些路走不通，全在历史对话里，新 Agent 看不到。

文件方案比聊天记录好。Claude Code 有 `CLAUDE.md`，Cursor 有 `.cursor/rules`，把项目约定写成文件，Agent 启动时读一遍。但这些文件是 Agent 各自为政的。你在 Claude Code 里花了三天调教出来的偏好，切到 Cursor 就得重来。

向量数据库提供了另一种思路：把所有内容向量化，用相似度搜索召回。但大多数 Agent 记忆是个黑箱：文本进去，向量出来，没人能看到实际存了什么。检索出了问题，也没法排查是存错了还是搜错了。

OpenViking 选了另一条路：把上下文组织成文件系统。Agent 用 `ls`、`tree`、`read`、`grep` 导航，每个目录都能打开检查。存了什么、缺了什么，一目了然。

OpenViking 的核心抽象是 `viking://` 虚拟文件系统。它位于 Agent 背后，是一个共享的上下文层。三种上下文类型各有分工。Resource 存事实和依据，Memory 存从交互里学到的经验。Skill 存做事的方法。

这个循环的关键在于"分层"和"提交"两个动作。分层让 Agent 不用一次性读完所有内容，提交让每次会话的经验不会随对话结束而丢失。OpenViking 把这两个动作做成了文件系统的原生操作：读目录读到的是摘要，不用翻原文；提交会话写下来的是文件，不会丢。

  <Section canvas id="filesystem">
    <SectionHead
      index="04"
      kicker="深入"
      title="viking:// 的目录结构"
      lead="三种上下文，各有各的路径。"
    />
    <Prose tile>

`viking://` 的目录结构遵循一套固定的命名规范。`resources/` 放全局共享的知识，`user/` 是每个用户的私有空间，`agent/` 存账号级共享的技能。`~` 是当前用户根目录的别名，`viking://~/memories/` 展开后就是 `viking://user/{user_id}/memories/`。

    </Prose>
    <CardGrid>
      <InfoCard label="RESOURCES" title="全局知识空间">
        <p class="mt-2 text-[13px] leading-[1.65] text-muted"><code>viking://resources/</code> 下按项目或主题组织。文档、代码、网页都可以导入，支持定时刷新远程源。所有用户可见。</p>
      </InfoCard>
      <InfoCard label="USER" title="用户私有空间">
        <p class="mt-2 text-[13px] leading-[1.65] text-muted"><code>viking://~/</code> 下包含 <code>memories/</code>（记忆）、<code>resources/</code>（私有资料）、<code>skills/</code>（私有技能）、<code>sessions/</code>（会话归档）。只有当前用户可见。</p>
      </InfoCard>
      <InfoCard label="AGENT" title="账号共享空间">
        <p class="mt-2 text-[13px] leading-[1.65] text-muted"><code>viking://agent/skills/</code> 存放账号级共享的技能定义。所有用户可见。endpoint、tool、payment 等子目录在规划中，尚未开放 API。</p>
      </InfoCard>
    </CardGrid>
    <Prose tile>

记忆类型不止"偏好"一种。OpenViking 支持 profile、preferences、entities、events、identity、soul、cases、trajectories、experiences 等多种记忆类型，也支持自定义类型。其中 experiences 会触发 Agent Evolution 流水线：把任务组织成 case，记录执行轨迹（trajectory），从中提炼可复用的经验。这套流水线默认关闭，需要显式开启 `agent_evolution.enabled`。

底层存储方面，OpenViking 用 Rust 写的 RAGFS 文件系统做 in-process 绑定（`ragfs_python`），文件系统逻辑直接在 Python 进程内执行，不再支持旧的 HTTP 客户端模式。预编译的 wheel 里自带 RAGFS 共享库，也可以从源码构建。

    </Prose>

切换的时候，前一个 Agent 做过的事情很难原封不动地传给下一个。人工写 handoff 说明既容易丢信息，也会让后一个 Agent 重复理解。OpenViking 在这里承担的是项目上下文中枢的角色，让不同阶段的材料各归其位。

接入方式也不复杂。OpenViking 提供了一键安装脚本，支持 Claude Code、Codex、Cursor、Trae、OpenCode 等主流 Agent，通过 Hooks + MCP 的方式接入。在控制台选择对应的 Agent，点击"复制为 Markdown"，把内容粘贴给 Agent 就能自动完成安装。托管服务前 50 个文档免费，自托管需要 Python 3.10+ 和一个 embedding 模型。
