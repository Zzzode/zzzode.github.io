<Prose>

先给口径：本文事实来自 NanoClaw 官网（nanoclaw.dev，2026-09-23 核对）、[Docker 官方博客 2026-03 的集成文章](https://www.docker.com/blog/nanoclaw-docker-sandboxes-agent-security/)与 [SiliconANGLE 的融资报道](https://siliconangle.com/2026/05/20/nanoco-raises-12m-accelerate-nanoclaw-secure-enterprise-grade-agentic-ai-assistant-every-office-worker/)；代码规模等数字是官网自述口径，随版本变化。文中架构判断是我基于公开材料的归纳。NanoClaw 与前一篇 [E2B](/posts/2026-09-23-e2b-sandbox-infra/) 讨论的是同一类问题的两个极端解法——一个卖云原生 microVM，一个让你在自己机器上用 Docker 跑。

</Prose>

    title="前因：个人智能体卡在「好用」和「敢装」之间"
    lead="让 AI 助手住进你的微信/Slack、替你操作文件和密钥，这件事的门槛从来不是模型能力，而是信任。"

  <Prose>

2025 年起，一类新产品形态出现：**消息应用里的个人智能体**。你在 WhatsApp、Telegram 或 Slack 里给它发消息，它替你查日历、整理文件、跑定时简报、操作各种 SaaS。相比 IDE 里的编程助手，这类助手有两个新特征：它**常驻**、它**贴近你的私人身份与凭据**。

早期开源玩家（以 OpenClaw 为代表）很快走向「大而全」：一个单进程塞进所有通道、所有提供商、所有工具，共享同一块内存。能力很多，代价是代码量膨胀到数十万亿行级、直接依赖数十个、配置文件几十个——普通人既看不懂也审不动，而它恰恰握着你的消息和密钥。

NanoClaw（由 NanoCo 维护，2026 年 5 月拿到 1200 万美元种子轮，Valley Capital Partners 领投，Vercel、Hugging Face CEO 等参投）把矛头直接对准这一点：**它提供同样的核心能力，但代码量小到你真的能读懂**。2026 年 3 月又与 Docker 官方集成，把会话容器升级为基于 microVM 的 Docker Sandbox。

  </Prose>
</Section>

    </span>
  </DualCompare>
  <Prose>

这张表最有价值的不是「谁赢了」，而是它点出了智能体安全的一条原则：**当你打算给智能体开 `--dangerously-skip-permissions` 之类的全自动模式时，它必须被关在一个可以随时丢弃的环境里**。Docker 博客把这句话说得很直白——microVM 隔离让「免确认放权」第一次可以在生产中接受，因为影响范围被物理地限制住了。这和 E2B 的思路殊途同归：自主权要扩大，先得有东西兜底。

  </Prose>
</Section>

      { title: "容器内推理执行", body: "智能体在容器内用选定的提供商（默认 Claude，安装时可选 Codex，之后可加 OpenCode、Ollama）运行；要执行命令、装包都在容器里，宿主无感。" },

    ]}
  />
  <Prose>

注意它的边界划分：**宿主只做路由，容器才做智能体**。宿主不碰模型、不碰业务逻辑；容器之间不共享内存，只通过 SQLite 队列与宿主通信。这套设计用最朴素的手段（单进程 + 容器 + SQLite）回避了微服务与消息队列的复杂度，同时拿到了操作系统级的隔离。

  </Prose>
</Section>
