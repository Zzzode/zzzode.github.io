  <Prose tile>

Lean 是一个开源编程语言兼证明助手，代码和证明写在同一种语言里。它的工作方式是：你先把现实中的程序抽象成一个数学模型，状态有哪些、状态之间怎么迁移都写清楚；然后写下你认为必须成立的性质，也就是定理，比如「每个 turn 最终只会产出一个 result」。Lean 内核会逐行检查证明，任何一步跳不过去就拒绝编译。

它和测试的区别是覆盖方式。测试选若干个具体输入跑一遍，能覆盖你想得到、且构造得出来的场景。证明面对的是模型允许的全部状态和全部交错顺序：只要存在一个反例，定理就证不出来，而 Lean 会把这个反例的构造路径直接吐给你。并发缺陷大多藏在两个事件罕见的先后次序里，单靠人写测试很难恰好排到，这正是状态机证明最擅长的地形。

这次的模型只描述状态和迁移，不重新实现算法。六个模型分别对应六段代码：SSE 字节流解析（stream）、重试退避（withRetry）、query.ts 的 turn 循环、引擎 turn 调度（engine）、会话权限阶段（session phase）、SDK 控制协议。模型文件里给每个迁移标注了对应的源码 file:line，并写明各自假设了什么、不证明什么。

下面先用一台三个状态的小机器，把模型、定理和内核怎么协作走一遍；每个例子都在稳定版 Lean 4.34.1 上实跑过，你也可以原样复现。

</Prose>

  <Prose tile>

**先看一条最短的证明。** Lean 有个听上去奇怪、用起来省事的设定：命题就是一个类型，证明则是一个符合该类型的「项」，写证明和写程序是同一件事。最短的证明只有一行：

```lean
theorem one_plus_one : 1 + 1 = 2 := by rfl
```

冒号右边的 `1 + 1 = 2` 是命题（也就是类型），`by` 之后进入 tactic（策略）模式，`rfl` 这条 tactic 的意思是「等号两边按定义就是同一个东西」。内核逐条 tactic 检查，哪一步化简不出它声称的结果，整份文件编译不过。同一个证明也可以不进 tactic 模式，直接写成一个项：

```lean
theorem one_plus_one' : 1 + 1 = 2 := rfl
```

实际写起来，VS Code 右侧的 Infoview 窗口会跟着光标显示「现在还剩什么目标」。整个过程更像逐步约分：每用一条 tactic，目标就矮一截，直到什么都不剩。

</Prose>

  <Prose tile>

**把一台状态机搬进 Lean。** 六个真实模型比这复杂得多，骨架却和下面这台三状态的小机器一模一样。先用 `inductive` 把状态有哪几种写死：

```lean
-- 一台微型任务机：等待 → 进行中 → 已完成
inductive State where
  | idle       -- 等待
  | running    -- 进行中
  | done       -- 已完成

-- Step s t 读作「允许从 s 一步走到 t」；三条构造子就是三条合法迁移
inductive Step : State → State → Prop where
  | start  : Step .idle .running
  | finish : Step .running .done
  | reset  : Step .done .idle
```

这里没有一行描述「怎么执行」，只规定什么事情被允许发生，和真实模型一样：只刻画状态与状态之间的迁移，不重写算法。「零步或任意多步可达」也用一个归纳类型表示：要么停在原地，要么先走若干步、再走一步。

```lean
inductive Steps : State → State → Prop where
  | refl : ∀ {s}, Steps s s
  | tail : ∀ {s u t}, Steps s u → Step u t → Steps s t
```

</Prose>

  <Prose tile>

**写下不变量，让机器把走法逐条摊开。** 要守的性质是：一步走到 `done` 的，上一步必须是 `running`，不许从 `idle` 直接跳成「已完成」。

```lean
theorem no_skip_to_done {s t : State}
    (h : Step s t) : t = .done → s = .running := by
  intro ht      -- 假设：这一步走到了 done
  cases h       -- h 是哪一条迁移？三条构造子逐条交代
  · cases ht    -- start 到的是 running，与 ht 矛盾，分支直接消失
  · rfl         -- finish：上一步正是 running，目标化为等式
  · cases ht    -- reset 到的是 idle，与 ht 矛盾，分支直接消失
```

关键在 `cases h`：它不替你假设 h 是哪一条迁移，而是把三条构造子全部摊开，逼你逐条通过。两个分支与假设矛盾，自动消失；剩下一个靠等号自反结束。小机器只有三条分支；换成真实模型，一个定理下面挂着全部迁移规则，分支随状态和事件组合迅速膨胀，六个模型这样逐条过下来，一共 1,529 条定理。小机器这一条定理就够了；真实证明还会对 `Steps` 做一次结构归纳，把单步性质提升到任意长度、任意交错的事件序列。测试要你自己碰巧排出那个罕见顺序，证明则不允许漏掉任何一个。

</Prose>

  <Prose tile>

**证明卡住的地方，反例自己浮出水面。** 现在给机器偷加一条坏迁移，对应这次 stream 缺陷的形状：半截响应被当成成功交付，不经过 `running`，从 `idle` 一步直跳 `done`。

```lean
inductive BuggyStep : State → State → Prop where
  | start : BuggyStep .idle .running
  | skip  : BuggyStep .idle .done   -- 坏迁移：没经过 running 就完成
```

原封不动证同一个定理，`cases` 摊开两个分支：`start` 分支照常消失，`skip` 分支留下一个怎么都消不掉的目标：

```lean
theorem buggy_no_skip {s t : State}
    (h : BuggyStep s t) : t = .done → s = .running := by
  intro ht
  cases h
  · cases ht
  · cases ht   -- 亮红：skip 分支留下一个证不出来的目标
```

编辑器在这里标红，Lean 给出的报错就是这个样子：

```text
error: unsolved goals
case skip.refl
⊢ State.idle = State.running
```

`State.idle = State.running` 不成立；卡住的分支叫 `skip`，分支上那条 `idle → done` 就是现成的反例路径：照它走一步，性质即被破坏。这次 19 个直接来自证明的缺陷都是这种结构的放大版：agent 从卡住的分支读出触发顺序，哪个事件先到、哪个取消迟到，再回 main 写成测试。

想视而不见也有办法：写一个 `sorry`，编译立刻放行，但内核每次都会留下警告：

```lean
theorem buggy_with_sorry {s t : State}
    (h : BuggyStep s t) : t = .done → s = .running := by
  intro ht
  cases h
  · cases ht
  · sorry   -- 编译放行；警告：declaration uses 'sorry'
```

最终审计的「0 sorry」，就是没有一条定理靠这种占位符过关。

</Prose>

  <Prose tile>

**一条命令，把审计落到字面。** `#print axioms` 列出一条定理背后用到的全部公理。在上面两段代码上各跑一次：

```lean
#print axioms no_skip_to_done
-- 'no_skip_to_done' does not depend on any axioms

#print axioms buggy_with_sorry
-- 'buggy_with_sorry' depends on axioms: [sorryAx]
```

第二行暴露了 `sorry` 的真面目：它是一条叫 `sorryAx` 的公理。录屏里「只用 `propext`、`Classical.choice`、`Quot.sound` 三条标准公理」的审计，就是用这种逐定理检查完成的：任何结论都不许站在临时塞进来的自定义前提上。

</Prose>

<Section canvas id="method">
  <SectionHead
    index="06"
    kicker="为何是现在"
    title="等了三十年，建模这一步突然便宜了"
    lead="用数学证明软件正确性并不新鲜。新鲜的是，过去最贵的那一步，也就是把几万行真实代码手工抽象成模型，现在模型自己就能做。"
  />
  <Prose tile>

形式化方法有成熟的家谱。Leslie Lamport 的 TLA+ 专门描述并发和分布式系统的状态迁移；2015 年 Amazon 在《美国计算机协会通讯》发表论文，记录他们用 TLA+ 检查 S3、DynamoDB 等系统的设计，在写代码之前就找出深层缺陷。Boris 在原帖里也说，他平时把 Lean 和 TLA+ 搭配使用：一个管数据与实现层面的严格证明，一个管数据流、并发和状态管理的设计建模。

这类方法一直没普及到普通业务代码，瓶颈很具体。建模要由既懂证明语言、又懂这个系统全部暗角的人手工完成，成本以人月计，模型还会随代码过时。测试框架之所以赢，是因为它便宜。

LLM 恰好卡在这个瓶颈上。Opus 5.5 的定位就是长程 agentic coding，百万 token 上下文装得下整个代码库，它可以直接读 TypeScript 源码、写出对应的 Lean 模型、再用同一套工具编译和迭代证明。这次从一句话到六个模型首轮通过只用了约三个小时（22:03 到 01:07），之后整夜加白天的时间主要花在复现、修代码、再证明、回应评审上。建模不再是瓶颈，证明助手本身成了流水线里最不知疲倦的那一环。

</Prose>
