    title="Lean 证明到底在证明什么"
    lead="看不懂 Lean 也能看懂这件事的分量，只需要分清三样东西：模型、定理、内核。"

  <Prose tile>

Lean 是一个开源编程语言兼证明助手，代码和证明写在同一种语言里。它的工作方式是：你先把现实中的程序抽象成一个数学模型，状态有哪些、状态之间怎么迁移都写清楚；然后写下你认为必须成立的性质，也就是定理，比如「每个 turn 最终只会产出一个 result」。Lean 内核会逐行检查证明，任何一步跳不过去就拒绝编译。

它和测试的区别是覆盖方式。测试选若干个具体输入跑一遍，能覆盖你想得到、且构造得出来的场景。证明面对的是模型允许的全部状态和全部交错顺序：只要存在一个反例，定理就证不出来，而 Lean 会把这个反例的构造路径直接吐给你。并发缺陷大多藏在两个事件罕见的先后次序里，单靠人写测试很难恰好排到，这正是状态机证明最擅长的地形。

这次的模型只描述状态和迁移，不重新实现算法。六个模型分别对应六段代码：SSE 字节流解析（stream）、重试退避（withRetry）、query.ts 的 turn 循环、引擎 turn 调度（engine）、会话权限阶段（session phase）、SDK 控制协议。模型文件里给每个迁移标注了对应的源码 file:line，并写明各自假设了什么、不证明什么。

</Prose>

  <Callout eyebrow="两个必须懂的审计词">
    <p><strong>sorry：</strong>Lean 里的占位符。写上 sorry，定理不用给证明也能通过编译，内核只给一个警告。一个「证明了」的模型里如果留着 sorry，等于这几条定理是空口说白话。最终审计明确是 0 sorry。</p>
    <p style="margin-top:10px"><strong>三条标准公理：</strong>Lean 自带 <code>propext</code>、<code>Classical.choice</code>、<code>Quot.sound</code> 三条基础公理。这次最终审计要求只允许使用这三条，没有额外塞假设，意味着结论没有建立在自定义的、可能作弊的前提上。</p>

<Section canvas id="method">
  <SectionHead
    index="06"
    kicker="为何是现在"
    title="等了三十年，建模这一步突然便宜了"
    lead="用数学证明软件正确性并不新鲜。新鲜的是，过去最贵的那一步，也就是把几万行真实代码手工抽象成模型，现在模型自己就能做。"
  />
  <Prose tile>

形式化方法有成熟的家谱。Leslie Lamport 的 TLA+ 专门描述并发和分布式系统的状态迁移；2015 年 Amazon 在《美国计算机协会通讯》发表论文，记录他们用 TLA+ 检查 S3、DynamoDB 等系统的设计，在写代码之前就找出深层缺陷。Boris 在原帖里也说，他平时把 Lean 和 TLA+ 搭配使用：一个管数据与实现层面的严格证明，一个管数据流、并发和状态管理的设计建模。

这类方法一直没普及到普通业务代码，瓶颈很具体。建模要由既懂证明语言、又懂这个系统全部暗角的人手工完成，成本以人月计，模型还会随代码过时。测试框架之所以赢，是因为它便宜。

LLM 恰好卡在这个瓶颈上。Opus 5.5 的定位就是长程 agentic coding，百万 token 上下文装得下整个代码库，它可以直接读 TypeScript 源码、写出对应的 Lean 模型、再用同一套工具编译和迭代证明。这次从一句话到六个模型首轮通过只用了约三个小时（22:03 到 01:07），之后整夜加白天的时间主要花在复现、修代码、再证明、回应评审上。建模不再是瓶颈，证明助手本身成了流水线里最不知疲倦的那一环。

</Prose>

    tile
        steps={[
      { title: "从代码生成模型", body: "agent 读真实 TypeScript，写 6 个 Lean 4 模型：状态、迁移、要守的不变量，每条迁移标注源码位置，并声明假设边界。" },
      { title: "独立复审模型", body: "模型写完后再逐行对照真实代码复审，防止模型把真实行为理想化。凌晨 engine 模型与真实运行对不上，结论被直接标为临时有效。" },

      { title: "证明反哺设计", body: "修复后再用同一份模型做简化：合并重复路径，让定理持续保护改动；人负责逐 PR 审批，机器负责等价性。" },

整条链路上有两道防自欺的关卡。第一道朝内：模型可能错，所以有 520 条真实 trace 的反向回放、有「先红后绿」的测试纪律、agent 还两次主动发更正（一次承认 engine 证明暂作临时结论，一次纠正自己对 #72130 退出保证覆盖范围的表述）。第二道朝外：每个 PR 都要人按批准，Boris 本人盯完全部 16 个；自动合并只在批准之后打开。证明保证的是「代码符合模型」，模型是否刻画了真实世界，靠证据和人共同兜住。

</Prose>

再往后看，这件事的意义可能比 24 个缺陷大。Agent SDK 是别人用来在生产环境跑长任务的库，它的状态机要处理取消、重试、权限、流式中断，这些都是传统测试最难做厚、而出错代价最高的部分。当建模成本趋近于一次对话，「给关键状态机配一份可机检的模型」可能从奢侈的学术流程，变成基础设施软件的常规工种。Boris 原帖最后只补了一句：TLA+ 也很好用，他常把两者结合起来找数据流、并发和状态管理的问题。工具的门槛在消失，方法没那么神秘，剩下的是愿不愿意把性质写下来。
