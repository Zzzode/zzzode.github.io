个人代码项目常常卡在工作交接处：实现模型结束后，人把代码发给审查模型；审查模型找到问题，人再把意见搬回去；会话停了，人补一句“继续”。即使代码大多由模型完成，决定下一步和推动工作的人仍然没有离开。

个人 Agent 公司要接管这些日常经营工作。人给出项目使命、资源上限和需要自己决定的重大事项；系统在这些条件内观察问题，形成目标，自主选择优先级，再把目标推进到交付。它也负责判断什么工作不值得做，什么时候应该等待新证据。长期目标足够清楚，Agent 就应能据此建立后续的多个工作项。

这里的“公司”是职责和授权的组织方式，不涉及公司注册，也没有证明系统已经可以自动赚钱。本文讨论的是个人代码项目的设计蓝图。产品能力采用官方说明，开源机制核对固定源码；后面的 PocketTasks 案例、预算和版本变化均为教学设计，没有运行一家真实的自主 Agent 公司。

### 自主经营与 RSI 解决不同问题

RSI 是 Recursive Self-Improvement，即递归自我改进。个人项目最容易着手的对象是 Harness：围绕模型运行的提示词、工具、上下文管理与执行流程。模型权重可以保持不变。若改进器本身也根据已有经验改变候选生成和选择方式，就进一步触及“怎样改进自己的改进方法”。

[Sakana AI 的 DGM](https://sakana.ai/dgm/)展示了改写 Agent 代码、用编程任务评测、保留不同变体继续探索的研究路线。[Harness²](https://arxiv.org/abs/2610.14224)则区分当前任务上的执行配置改进，以及跨任务保留的改进经验。关于其具体递归过程，可接着读[本站的 Harness² 源码文章](/posts/2026-10-19-harness2-recursive-agent-harnessing/)。

<Section canvas id="system-architecture">

本文选择一套具体的起步架构：单台持续在线的 Linux 主机，运行 TypeScript 控制服务和 PostgreSQL；编码会话由 Claude Agent SDK 在受限容器里按需启动。一个仓库起步只允许一个代码写入者，读代码、审查和收集证据可以按配额并行。没有工作时不调用模型。这个选择面向个人持有、规模有限的代码项目，属于本文的工程建议。

控制服务采用模块化单体：代码在一个工程里，模块之间通过明确函数和持久对象交接。部署时把可信的控制进程与执行不可信代码的进程分开。暂时不引入微服务，也不让公司里的每个角色都成为常驻服务。

### 先把进程画清楚

常驻的 `control` 进程接收信号，处理事件，维护业务状态，决定是否需要调用某个角色。常驻的 `runner` 进程负责领取执行作业、准备容器、启动模型会话并收回产物。两者可以出自同一个代码包，但使用不同凭据。PostgreSQL 保存权威状态；本地制品目录保存大型日志和验证产物，数据库保存它们的哈希与引用。

`control` 内部有五个模块。`intake` 将 CI 失败、Issue 与周期扫描统一成 Signal；`portfolio` 调用经营 Agent，决定接受哪个目标；`planning` 接受计划者生成的任务依赖图；`scheduler` 根据依赖和配额生成执行作业；`reducer` 接收执行、验证和审查结果，推进状态。`policy` 是它们共同调用的授权检查模块。它们都在控制服务内，不需要单独的网络服务。

`runner` 不决定产品方向。它把某条 Job 变成 Attempt，运行时固定任务合约、代码版本、策略版本及 Harness。`verifier` 运行项目登记的验证项并采集结果；它属于执行侧，但使用独立于实现者的环境与证据回传身份。`integrator` 是唯一能更新目标分支的受信组件。`improver` 则按周期消费失败轨迹，提交新的 Harness 候选。

### 模型在哪些地方作决定

经营 Agent 判断工作值不值得做，计划 Agent 决定怎样拆分，实现 Agent 选择局部实现，审查 Agent 寻找遗漏。程序负责校验权限、领取任务、记录状态和触发下一步。模型可以重写计划，验收规则与总预算仍按已批准的策略执行。

例如，计划者输出“先复现，再分别修改代码和编写进程场景”。控制服务检查依赖图后保存任务。此后谁可以启动、结果是否过期、是否该发起审查，都由状态机处理。实现失败后，只要存在普通返工路径，程序就生成返工作业，再按需要调用模型调整方案。人不用在两个窗口之间转述意见。

这里没有要求业务流程永远固定。Agent 可以增加诊断任务、改变依赖或放弃低价值目标。固定的是提交这些变化时必须满足的约束，以及“什么算已经完成”的判定过程。这样既保留模型的规划能力，也让运行可以解释和恢复。

### 为什么这里不把所有框架都接上

[Symphony](https://github.com/openai/symphony/blob/be10a1b79df723d6d7612b5651c8522704dafb2e/README.md)可以承担已有 Issue 的执行调度，LangGraph 可以管理图状态和检查点；[Temporal](https://docs.temporal.io/workflow-execution)适用于需要可靠恢复的长流程编排。本文默认方案由 PostgreSQL 和有限状态机承担任务状态，起步再套一层图状态与另一套任务队列，会产生多个“当前任务到底在哪一步”的来源。

已有 Symphony 或 LangGraph 系统时，应保留一个权威状态源，按它的恢复语义补经营能力。本文选择显式业务状态机，是为了把个人项目必须实现的转换写清楚，范围仅限这套代码交付流程。若后来需要维护大量跨服务的定时器、补偿流程与长时间等待，应重新评估成熟工作流引擎，避免继续扩建自制平台。

### 哪些技术事实已经核对

[Claude Agent SDK 官方说明](https://code.claude.com/docs/en/agent-sdk/overview)明确它可在 TypeScript/Python 中使用 Claude Code 的工具循环。[PostgreSQL 的 SELECT 文档](https://www.postgresql.org/docs/18/sql-select.html)说明 `SKIP LOCKED` 可用于多个消费者领取队列型表；它不适合拿来产生普通业务的一致性视图。[LISTEN](https://www.postgresql.org/docs/18/sql-listen.html)的注册随连接结束而清除，[NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html)则在事务提交后发送。因此任务保存在表里，通知仅提示控制器重新查询，丢一次通知仍能由扫描补上。

Git 的 [worktree](https://git-scm.com/docs/git-worktree)允许一个仓库有多个工作树，但不提供进程或凭据隔离。本文让容器拿独立源码副本，产物由可信进程收回。容器本身还需要文件和网络限制；[Docker 官方文档](https://docs.docker.com/engine/security/)也指出隔离效果取决于配置，不能仅凭用了容器就认定权限受控。

### 分派要有工具和结果通道

主控需要能创建任务、查询状态、给正在执行的会话补充信息，以及启动审查。若它只能在聊天里说“让另一个 Agent 去做”，却没有相应执行接口，分派仍会落回人身上。工具调用的结果必须进入任务记录，而不只是展示一句已发送。

可以把接口设计为 `create_task`、`assign_task`、`request_review` 和 `request_decision` 等受约束的动作。这些是本文建议的工具名称，实际系统可使用自己的 API。运行时检查目标任务、现有权限和资源余量，成功后返回任务或尝试标识；模型据此跟踪结果。

Agent 之间也不必互相广播完整对话。局部实现细节优先保留在证据文件里，给负责人一个短摘要和可追溯引用；发生矛盾时再取回原始记录。公司内的共享设计决定需要一个权威版本，由负责该问题的角色维护，避免两个计划者分别替同一接口作决定。

第一版可以让经营、计划、实现与审查使用同一个经过项目评测的模型，分别启动上下文。先把公司运行通路做对，再用项目轨迹决定哪些角色适合更便宜的模型。更贵的模型适合哪些判断、便宜模型能否可靠执行清楚的合约，都需要在自己的项目上测。此文不把某次厂商实验的模型组合当作通用答案。

### 哪些事件会唤醒经营 Agent

外部 CI 失败先以来源系统和运行标识去重，写入 Signal 与待处理事件。单纯心跳、同一失败的重复日志不会再次启动经营 Agent。新增独立失败、目标完成、计划无法继续，以及定期经营检查到期，才生成 OWNER Job。同一项目的经营 Job 合并尚未处理的线索，避免十条同源日志启动十个负责人。

经营 Agent 读取使命、当前目标摘要、资源余量与本次线索，返回 `CREATE_GOAL`、`ATTACH_TO_GOAL`、`DEFER` 或 `DISCARD`。`portfolio` 检查提案后提交：创建目标同时生成 PLAN Job；归并则把来源附到现有目标。它不会直接从日志跳到任意 Shell 命令。

优先级先分故障恢复、兼容维护与可选改进，再在同类中考虑影响、阻塞关系与等待时间。模型提供理由和等级，程序按已接受的优先级、依赖及公平性规则领取。计划者已经决定任务内容、责任角色与模型配置建议，经营者决定优先级和预算；程序只落实合法的就绪任务。这样，分派判断由 Agent 作出，启动与交接由程序保证，无须主控在聊天里点名“下一位请工作”。

### 线索需要怎样变成可决定的工作

一条“任务偶尔取消失败”还不足以安排实现。诊断角色先关联可复现的调用路径，保存输入条件与行为证据，并确认是否已有同类任务。若多个报错来自同一根因，就合并到一个目标中，避免多个 Agent 同时修同一个问题。

判断是否重复，需要比较问题本身。完全相同的日志可能由不同环境引起，不同日志也可能属于同一个资源释放缺陷。可以先用确定性的标识缩小候选，再让模型比较根因与影响范围。合并后的目标仍要保留原始引用，才能检查修复是否覆盖了不同表现。

优先级由经营负责人决定，但要能解释。对 PocketTasks，丢失用户结果或后台任务无法停止，应高于没有已知影响的内部整理；阻塞既定路线的缺陷，应高于一个刚想到的新功能。这里的排序是使命下的设计建议，应由项目自己的价值规则约束。

### 目标与候选池分别保存

目标表达希望改善的结果，例如“取消后后台写入可靠停止”；任务表达达成它的一部分工作，例如“复现进程仍在运行的路径”。负责人可以自主创建这些普通目标，也可以把探索性工作放进候选池，等待信息或配额更充分时再处理。

候选池不应成为无边界的愿望清单。每项至少有来源、预期结果和不处理的影响，过期后重新检查或删除。一个改进看起来有趣，却无法说明为何服务当前使命，可以不做。空闲期间，运行时等待相关事件或下一次经营检查；不必唤醒模型反复问自己还有什么可以重构。

### 合约定义可观察结果，给实现保留空间

[任务合约示例](/files/personal-agent-company/task-contract.example.json)记录上级目标、依赖、文件职责、验收条件与采用的 Harness 版本。示例中的逻辑验证项需要由目标项目映射成自己的原生命令；它不是可直接运行的服务配置。

```json
{
  "task_id": "T2",
  "goal_id": "G1",
  "depends_on": ["T1", "T3"],
  "owner_role": "implementation",
  "file_ownership": ["src/jobs/**", "tests/jobs/unit/**"],
  "harness_version": "H0",
  "budget": {
    "max_agent_seconds": 900,
    "attempts_before_replan": 2
  }
}
```

完成条件应写成“取消后，后台写入进程退出，目标文件不再增长”。“增加一个取消标记”只能描述实现手段，无法证明结果；“所有测试通过”又没有说明测试覆盖了什么。合约还要包含需要保留的旧行为，避免修好取消却破坏正常运行。

计划者不应在最初把所有函数结构写死。确定目标和接口约束后，执行者根据代码选择实现；若必须改变已约定的设计，则提交内部设计问题给负责的计划者。只有超出公司现有授权的部分才进入人的重大决策队列。

### 分派包含角色、工作区与验收责任

任务可以被重新分配。若原执行者反复在同一假设上失败，计划者应读取失败记录，改变任务大小或验证路径，再交给新的尝试。仅更换模型名称、把相同提示词重新发送，不足以说明策略已经改变。此前做过什么和为什么失败，要一起传给接任者。

### 如何领取任务而不抢单

先按项目锁定调度配额行，检查可用执行槽与预算。再从已经完成依赖检查的 READY 作业中取一条。使用 pg 时，事务内的语句必须复用同一个 client，不能用连接池随机分配的不同连接。下面只演示领取的锁与返回字段，参数 `$1` 是项目标识，不是一套完整的派发函数：

```sql
SELECT id, task_id, kind, generation
FROM jobs
WHERE project_id = $1
  AND state = 'READY'
  AND available_at <= now()
ORDER BY priority DESC, created_at ASC
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

在同一短事务里，控制器再核对任务和授权版本，登记预算预留，把 Job 改成 RUNNING，`generation` 加一，写入 Attempt 和 `attempt.claimed` 事件。任何一项失败就回滚。事务提交后才启动容器和模型，数据库锁不会一直持有到模型完成。

### 先把模型输出变成机器可读的对象

以下 TypeScript 片段接收 SDK 的结构化结果。实际应用需要提供 `prompt`、JSON Schema 和已经创建好的受限工作目录 `workspace`；这不是完整的公司启动程序。`query()`、`outputFormat` 和结果里的 `structured_output` 来自[官方结构化输出文档](https://code.claude.com/docs/en/agent-sdk/structured-outputs)，其余落库与授权逻辑由自己的系统实现。

```typescript
import { query } from "@anthropic-ai/claude-agent-sdk";

type PlanInput = {
  prompt: string;
  schema: Record<string, unknown>;
  workspace: string;
};

async function collectPlan(input: PlanInput): Promise<unknown> {
  for await (const message of query({
    prompt: input.prompt,
    options: {
      cwd: input.workspace,
      maxTurns: 12,
      outputFormat: { type: "json_schema", schema: input.schema },
    },
  })) {
    if (message.type !== "result") continue;
    if (message.subtype !== "success" || !message.structured_output) {
      throw new Error("Planner returned no usable structured result");
    }
    return message.structured_output;
  }
  throw new Error("Planner session ended without a result");
}
```

结果交回程序后，Adapter 还要完成运行管理，包括配置固定模型与角色提示词、工具集、外部超时和取消，保存会话标识与消息轨迹，并将失败交回运行器。不能因为 SDK 返回 `success` 就把 Task 标成完成；结构正确也不能证明计划正确。

`planning.acceptPlan()` 必须检查：目标仍在同一版本，所有任务服务原目标，依赖存在且无环，验收项有实际验证路径，文件职责没有未经处理的重叠，所需工具和预算属于现有授权。返回对象即使通过 Zod，也可能引用不存在的任务或提出越权行动。语法校验和业务校验需要分别做。

### 公司级委派与会话内子 Agent 要分开

SDK 可以在一次会话内调用子 Agent，适合局部调查。跨小时的实现、审查、重试与恢复，应作为数据库中的 Job 存在，由控制器启动独立会话。否则主会话退出后，子任务谁接任、谁拥有预算、哪个结果有效，都容易重新变成聊天历史里的隐含约定。

各角色共享的协议是 TaskContract 和结果对象。实现者提交候选与剩余问题；验证器提交实际执行证据；审查者返回 `PASS`、`REWORK`、`NEEDS_EVIDENCE` 或 `PLAN_CONFLICT`。控制器据此选择固定转换。最后一种回到计划者内部解决；它不自动代表需要人的判断。

### 不要让权限回调变成新的人工转接台

预先允许的日常操作由程序自动放行，超出角色能力的操作返回结构化拒绝原因。普通拒绝触发重新规划，只有确实需要改变公司授权才建立 Decision。不要把每一个工具权限弹窗直接转发给人，再声称系统已经自主经营。

[SDK 权限文档](https://code.claude.com/docs/en/agent-sdk/permissions)明确，`allowedTools` 表示自动批准规则，并不等于其余工具不存在；提前获准的调用也可能不经过 `canUseTool`。因此不能只在这个回调里检查权限。角色工具配置、必要的调用前检查和容器边界需要配合使用。

实现容器不连接任务数据库，不挂载发布凭据和 Docker Socket；模型 API 通过受限凭据通道访问。经营与计划角色不需要可任意执行 Shell 的宿主机权限。关于凭据代理和文件、网络边界，可以参考[官方部署说明](https://code.claude.com/docs/en/agent-sdk/secure-deployment)。这是减少无人值守误操作所需的运行边界，不能靠提示词替代。

### 分开检查实现、行为和经营结果

### 验证器也不能由实现者随意改写

`verification/registry.ts` 保存控制服务认可的验证项，绑定命令或场景、运行镜像、超时和要求版本。Worker 可以为项目增加测试，但不能在同一任务里移除必须通过的 Gate，不能修改受信验证器，也不能直接写 Evidence 表。命令登记在控制服务并不使项目测试代码自动可信，因此关键行为需要保留独立场景，按原始验收核对变更后的测试。

验证器在新的环境固定候选，采集原始退出状态及产物。实现者提交的“测试已通过”可作为调查线索，不能作为受信 PASS。审查也会检查测试是否被弱化。新场景第一次被加入时，要在已知失败版本和已知正确条件上检查它能否区分结果，否则错误的验证方法也可能被长期自动执行。

集成由单一 integrator 串行处理，所有提交先变成候选。文件职责约束由计划接纳和变更接收共同检查；代码冲突回到计划者，无法自动合并不意味着必须找人选文件。涉及公共接口承诺的不兼容方案，则按授权规则转成重大决策。

### 自动返工也需要收敛

审查报告应把缺陷交给负责的任务，保留证据并说明影响。实现者可以修复，也可以提出反证；争议回到主控核对原始验收，不必把每次意见冲突都升级给人。若争议其实来自产品承诺不清，再生成需要决定的产品问题。

重试不应只是累加次数。每次返工都要说清上一轮为什么没解决，以及新一轮将改变什么。持续出现同一失败时，系统可以缩小问题、补诊断或暂停该任务，继续推进无依赖的工作。负责人只有在现有授权无法给出下一步时，才向人提出决策请求。

审查成本也要有比例。清晰的局部修复，先跑确定性检查，再做有针对性的独立审查；复杂交互则需要更完整的运行证据。对每个小改动都召集许多审查模型，会让协调成本超过实际收益。架构应随模型和项目证据调整，保留真正有用的步骤。

### 谁负责唤醒下一次工作

调度程序接收任务事件或按周期检查。它核对依赖、资源和领取状态，把就绪任务交给工作进程；只有遇到需要判断的问题，才调用负责人或计划模型。这样的事件循环能够在一个模型会话退出后继续运行。

[Symphony 的实现](https://github.com/openai/symphony/blob/be10a1b79df723d6d7612b5651c8522704dafb2e/elixir/lib/symphony_elixir/orchestrator.ex)提供了一个具体例子：Worker 正常退出也会安排活动状态续跑检查；故障退出走另一个恢复路径。代码审阅支持这一行为说明，本文没有启动该服务验证实际调度。

下面是建议的调度伪代码，只表达职责顺序，不是某个框架可直接执行的 API：

```text
on_event(event):
    persist_once(event.id, event)
    reconcile_task_state_and_external_receipts()
    invalidate_evidence_for_changed_revisions()
    if a_business_decision_is_needed:
        proposal = call_responsible_agent(current_state)
        apply_only_if_allowed(proposal, current_policy)
    dispatch_eligible_tasks_with_atomic_claims()
    schedule_next_check_or_wait_for_event()
```

### 恢复时实际检查哪几件事

进程重启后，控制器先提交 LISTEN 注册，再查询未处理事件和到期 Job，之后才依赖通知唤醒；还保留周期扫描。启动顺序参考 PostgreSQL 对 LISTEN 建立时竞争条件的说明，避免先读完表、后订阅期间漏掉变化。

恢复器先检查 STARTING 或 RUNNING 的 Attempt，查询 `sandbox_id` 和运行器标签。模型进程退出但容器内子进程仍存活时，要清理整个尝试环境；仅杀主进程不能证明后台写入已停止。确认旧环境已停止或隔离，再撤销代次、回收作业并创建新尝试。旧尝试晚到的结果只归档，不能重新进入有效链路。

对 VERIFYING 或 REVIEWING 的 Task，检查对应 Job 是否存在。缺失时以原候选与要求版本重建去重 Job；已存在则继续等待或恢复它。对副作用 UNKNOWN 的交付操作先查外部回执，不直接重复执行。恢复不需要每次都调用负责人模型，大部分是确定性的核对。

### 存活、进展与完成，要分别观察

[运行策略模板](/files/personal-agent-company/runtime-config.example.json)用 15 秒心跳、60 秒租约、10 秒队列扫描和 300 秒无进展诊断作为教学设置，实际值需要根据任务时长调整。心跳可以说明进程仍然连接，不能证明它在有效推进。进展应结合阶段状态、产物变化、验证结果与失败假设判断。一个模型持续输出文字，却一直重复同一个无效命令，仍可能没有进展。看门狗应触发诊断或重新规划，保留停滞原因。

领取任务需要原子操作，避免两个执行者同时认为自己负责。租约是有期限的执行资格；新尝试取得新代次后，结果接收端只接纳当前有效代次。租约过期本身不会让旧 Shell 自动停止，所以还要终止或隔离过期进程，并为不同尝试使用隔离工作区。

外部副作用还需要核对。例如发布操作超时，不能直接认定没有发布。建议先保存操作意图和稳定的操作标识，再执行；重试前查询回执或外部状态。接口支持幂等键时，同一意图可用它避免重复创建；不支持时，仍需要查询与对账。任务数据库与外部服务之间不存在自动成立的一次性执行保证。

### 重大决策通过一个确定入口写回来

G2 要把本地工具改成账号与云同步服务，超出 M1。经营者生成[决策包 D1](/files/personal-agent-company/decision-packet.example.json)，给出维持本地、有限研究与改变方向等选项。控制器把 G2 标成 `NEEDS_DECISION`，保存问题、依据和等待期间的安排，经营报告只展示这一项需要人的选择。

可以把人的答复入口设计为 `POST /decisions/D1/answer`，载荷为选项、理由和 `expected_policy_version`。这是本文建议的 API。入口只接纳经过身份验证的决策者，并在事务中比对 P1：若授权已变化，答复标成过期并重新生成问题；若仍有效，则保存决定和新策略 P2，建立受影响目标的 PLAN Job。

批准有限研究后，计划者自行拆研究任务，运行器自行派发。人不需要继续选择执行模型或修改哪个文件。对 G1 的普通维护作业也没有重新逐条授权的必要；涉及新增限制的策略修改则立即撤销对应执行能力，不能让旧 P1 任务继续越过已经收回的权限。

### 交付到目标分支和对外发布怎样处理

integrator 使用目标分支的预期旧版本做条件更新；版本已经改变就重新构造和验证候选。外部发布另写 EffectIntent，执行后保存真实回执，超时则标为 UNKNOWN 并查询实际目标。默认未授予发布权时，以明确的交付包结束这次维护，不把每一次发布都伪装成“重大决策”。如果希望兼容补丁自动发布，应在初始章程授予有限发布权并规定门槛。

### 日常经营循环与改进循环分别运行

[Harness² 的双层递归](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/README.md)提供更进一步的参考：当前任务产生配置修改和行为对照，改进经验又帮助之后的改进。它的默认执行配置不是简单地永久叠加全部历史规则；经验如何选择和应用，本身就是需要管理的对象。

参考控制器从一开始就要求最终行为验证。H0 的问题是实现者没有尽早追踪后台进程，最终被 verifier 拦下并返工。改进器读取 A21 的轨迹和 E1，提出“在取消类任务中提前加载生命周期验证方法”这一假设。它创建 Harness 分支 H1，只修改如下 Skill。以下 diff 是教学候选，不是已产生收益的实测补丁：

```diff
--- harness/H0/skills/cancellation-verification.md
+++ harness/H1/skills/cancellation-verification.md
@@
-Run the module regression suite before submitting the candidate.
+For cancellation tasks, map the foreground and background process lifecycle.
+Load the registered process scenario and inspect its known-failure evidence.
+Check the acknowledged cancellation boundary and observe writer termination.
+Report any missing process capability instead of assuming the scenario passed.
+Run the module regression suite before submitting the candidate.
```

条件加载发生在 ContextBuilder，触发条件来自任务合约中的取消行为。普通文案修正不会带上这段方法。这里没有增加一种可由实现者随意决定是否执行的最终门槛，也没有改变 A1—A3；只是让实现者更早获得已经需要满足的行为知识。

### 一次试验如何从提案变成采用

`improvement.createExperiment()` 接受基线 H0、候选 H1、编辑范围和假设，固定回放清单、要求版本和预算。函数名称属于本文设计。回放从缺陷修复前的代码开始，H0 和 H1 使用同一模型、环境与验收，记录首次候选是否满足要求，以及计划、实现、验证、返工的总消耗。

开发集结果供改进器修改候选；保留集只做采用审核，不把预期修复直接交给实现者。关键要求有退化就拒绝，结果不确定则继续收集证据。全部试验结果写入记录，不只保留最幸运的一轮。本文未运行这些回放，因此采用状态仍是 `NOT_RUN`。

允许采用时，写入不可变的 Harness 快照及其哈希，在事务里更新新尝试使用的默认版本。已有 Attempt 仍使用启动时的 H0。有限采用中的真实任务如果出现同类退化，更新默认版本回 H0，并对受影响任务重新核对；已经发生的代码交付不能靠切回提示词自动撤销。

### H2 和 H3 怎样继续变化

H2 可增加一个受限辅助工具，把原始进程日志归并为退出事件、取消确认点与文件增长区间，输出原始引用。工具不拥有写 Evidence 表的权限；verifier 仍独立取得最终证据。评测要同时检查“节省诊断步骤”和“有没有把进程未退出写成退出”。如果只是让报告更漂亮，不能因此采用。

H3 修改审查的上下文选择策略：优先装入当前候选的要求、失败记录和原始证据，旧候选结论只作为历史。版本匹配早已是控制器的固定门槛，不把补上基础正确性冒充 RSI。H3 需要证明改善的是审查判断或效率，而不是删掉必须看的材料换来更低成本。

### H4 改变改进器的方法

假设改进器反复提出内容相似的候选，H4 可以修改 `improver/policy.json`，把逐条按日志尝试改成按根因聚类。下面是拟定的策略变化：

```json
{
  "before": { "sample_unit": "failure_log", "candidates_per_batch": 3 },
  "after": { "sample_unit": "root_cause_group", "candidates_per_batch": 3 },
  "frozen": ["authority", "evaluation_protocol", "total_experiment_budget"]
}
```

比较对象变成两个改进器版本：给定相同任务分布与总试验预算，哪个能提出更有用、重复更少的 Harness 候选。最终还要回到后续任务的行为与人为介入。如果只看到候选数量变少，尚不能证明改进方法变好了。改进器也不能自己改掉这次试验的采用标准。

### 改进权也有自己的边界

改进 Agent 可以提出新的验证方法或更好的任务拆分规则，但不应在同一试验里改变使命、放宽授权或降低判分条件。业务测试可以补充，新的评测也可以另行设计；被用来判定这次候选是否更好的评测基线需要固定。涉及授权变化的提议回到正常决策机制。

采用新版本时，保存基线、候选和采用依据，并留有退回旧版本的路径。有限采用后，还要观察真实任务的失败、成本与人为介入。回放表现较好，只证明它在那组条件下有效；对未来任务的影响需要继续观察。

  <Prose tile>

长期运行会积累不同性质的信息：任务现在在哪一步，某项设计为什么成立，以及某种办法过去为何失败。把它们混进一个不断增长的系统提示词，会让过期状态和局部教训影响所有工作。

[LangGraph 的持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)区分当前线程的检查点和跨线程的长期存储。它也明确提醒：保存在内存里的 Saver 不会跨进程重启保留。采用框架之后，仍须确认实际配置是否使用持久存储，以及保存内容是否足够支持自己的恢复过程。

### 经营事实与候选经验分开保存

任务完成、代码版本、外部回执属于经营事实，应有权威来源。经验条目则应保留来源任务、适用范围和反例。它可以先作为候选建议，验证后再成为默认执行规则。经验过期或被新版本推翻时，应能撤回。

### 每个角色到底拿到哪些上下文

上下文构建器按角色生成 ContextBundle。经营者读使命、目标组合、当期资源和新增线索；计划者多读代码索引与设计决定；实现者拿任务合约、依赖产物、必要代码和本任务失败；审查者拿原始要求、候选差异与验证证据，避免只听实现者解释为什么正确。

经验先按项目、相关文件、失败类别和 Harness 适用版本检索，加载匹配条目的摘要与引用。模型需要时再取原始证据。每次 Attempt 保存使用过的条目 ID 与版本；后来发现经验错误，可以追踪受影响的尝试并撤回该规则。第一版用结构字段和普通文本检索即可，不能因为用了向量库就省掉版本与适用范围。

### 预算如何约束自主经营

开始作业前，程序在项目预算周期内预留配额，并把预留关联到 Attempt。结束后按实际结果结算；超时且消耗未知时先保留估计上限，之后核对。资源判断必须与领取在同一事务规则下执行，不能让两个并发角色都看到同一份未预留余额。

本文示例限制 Agent 执行时间，这与供应商账单金额不同。一次正在飞行的模型请求，也不能靠终止本地进程保证账单精确停在指定金额。要控制花费，需要同时设置调用预算、供应商可用的账户限制和运行器超时，并保留误差。总预算内重新分配由经营者完成；预算耗尽后等待新周期，不反复催人加钱。

### 优先测人是否真的少介入

个人项目的首要质量条件是关键行为和必要回归没有退化。满足这些条件后，再比较人为介入、耗时和资源。不能为了让自动完成比例更高，就把需要验证的行为移出验收，或者把复杂任务都留给人处理。

建议同时记录接收了哪些任务、拒绝或延后了什么，以及最终实际完成的目标。任务难度变化会影响比率，单看某一周完成比例，无法区分系统进步和选择了更简单的工作。

### 评测改进器时，保留未用于调优的任务

历史任务回放应从修复前的代码版本开始，在隔离环境中比较 Harness；泄露修复结果会改变问题难度。开发回放集用来产生和选择候选，保留任务用于采用审核。不断反复试探同一保留集，也会产生间接过拟合，因此长期运行需要补充新任务和更新评测协议。

有噪声的结果要保留重复运行和失败分布，不能只取一次最好的输出。没有可靠自动判分器的任务，可以结合运行证据和模型评估，但应保留不确定性。审查模型自身也需要校准，已知通过与已知失败的案例可以帮助检查它是否过宽。

评价公司的表现，可以保留多项结果。先满足关键行为，再比较对人的依赖与资源代价，通常更容易解释。一个更省钱但经常错误宣布完成的版本，不应因总分抵消而自动采用。

这一版没有部署 Agent 公司。把文中的设计变成软件，仍要实现上述入口和事务、接通实际仓库与模型账户，并按最后一章的故障场景取得证据。下载表结构和配置只能帮助开始工程，不能代替这些实现。
